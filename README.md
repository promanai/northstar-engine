# Northstar Engine

Open-source MVP движка для простых AI-сайтов, который разворачивается в собственном Cloudflare account клиента.

Статус: разрабатываемый MVP, **не готовый production-релиз**. Полный проверяемый чеклист и оценка — [PROGRESS.md](PROGRESS.md). Термин «open-source» описывает цель проекта: лицензию для распространения ещё нужно выбрать и добавить.

Проверка выпуска: после сборки `npm run test:acceptance` выполняет локальный сквозной сценарий Standard от пустой базы до восстановления backup и повторного входа. Рабочие данные и облако не затрагиваются. [Покрытие и оставшаяся приёмка](docs/STANDARD_ACCEPTANCE.md).

Для уже развёрнутого Standard: `npm run check:standard -- --url https://YOUR-SITE.example --expect-build dist/engine-build.json --report outputs/smoke.json`. Паспорт нужно взять из ожидаемой сборки; без `--expect-build` версия сервера не проверяется. Только GET-проверки, без развёртывания и изменения бизнес-данных; административная проверка требует отдельно подтверждённого origin и сессии. [Облачная приёмка](docs/CLOUD_ACCEPTANCE.md) и [паспорт сборки](docs/BUILD_IDENTITY.md).

## Lite по умолчанию

Перед созданием клиентского сайта пройдите [паспорт запуска](docs/LAUNCH.md): вопросы владельцу от целей и favicon до полномочий AI, домена и приёмки. В комплекте [чеклист с графом](docs/LAUNCH_CHECKLIST.md), машиночитаемый шаблон и локальный инструмент `npm run launch -- init --mode lite`. Для заполнения без редактирования JSON: `npm run launch:ui` — вопросы, граф, импорт и сохранение в файл. Ответы владельца не публикуются на сайте.

Простой сайт теперь запускается без базы и файлового хранилища: `npm ci`, `npm run build`, `npm run start`. Контент, каталог, тема и фон — в `site.config.json`. AI-чат держит историю только в памяти вкладки. MCP предоставляет публичное чтение; кабинет, админка, заказы, платежи и загрузки отключены. Для размещения используйте `deployment/lite.example.json`. [Настройка Lite и переход на Standard](docs/LITE.md).

## Что есть в Standard

Управление собственными активными сессиями в профиле: просмотр, завершение отдельного входа или всех остальных с текущим паролем и подтверждением. Текущая сессия и ключи AI-агентов сохраняются. Нужна индексная миграция 0019. [Правила и ограничения](docs/SESSIONS.md).

Обзор администратора с реальными счётчиками клиентов, диалогов, заказов, бронирований и обращений за 24 часа/7/30 дней. Текущие задачи и последние обращения, переходы в рабочие разделы, без демонстрационных цифр. [Правила подсчёта и ограничения](docs/OVERVIEW.md).

Автоочистка аналитики по часовому расписанию: ограниченные порции просроченных событий, защита от одновременной смены срока хранения и безопасный пропуск в Lite. Работает после включения Cron Trigger в конфигурации Standard, без новых миграций. [Настройка и ограничения](docs/ANALYTICS.md#фоновая-очистка).

Внутренняя аналитика в `/admin#analytics`: периоды 24 часа/7/30/90 дней и свой диапазон, источники, страницы, клики, пути посещений и оригинальная переписка с ассистентом. По умолчанию сбор выключен; включается администратором и требует согласия посетителя. Нужна миграция 0018. Lite без базы не меняется. [Настройка, приватность и ограничения](docs/ANALYTICS.md).

Обращения клиентов: переписка в `/account#tickets`, ответы и статусы в `/admin#tickets`, приватная история в D1 и общий REST/MCP с отдельными полномочиями. Повторы защищены ключом идемпотентности, одновременные ответы — проверкой версии. Нужна миграция 0017. Email/SMS-уведомлений и автоматических AI-ответов пока нет. [Контракт и ограничения обращений](docs/TICKETS.md).

Надёжная отправка чата: обязательный `Idempotency-Key`, возврат сохранённого результата без нового AI-вызова, сериализация ходов одного диалога и защита от поздних ответов. Для обновления нужна миграция 0016 и обновлённые API-клиенты. Lite остаётся без базы. [Контракт и ограничения](docs/CHAT-RELIABILITY.md).

После перезагрузки Standard восстанавливает состояние незавершённой отправки через приватный `GET /api/chat/request`. Браузер сохраняет только идентификатор попытки, а историю получает из D1 с повторной проверкой доступа; новых AI-запросов восстановление не создаёт. Неотправленные черновики не сохраняются. Дополнительная миграция сверх 0016 не требуется.

Общая квота платных AI-попыток: дневной/месячный потолок на весь сайт, атомарное резервирование до обращения к провайдеру, остатки в админке. При недоступности D1 платная генерация закрывается. Нужна миграция 0014. Это не лимит расходов в валюте; Lite без базы получает только серверный запрет новых платных запросов. [Настройка и ограничения](docs/AI-QUOTAS.md).

Управление ассистентом и клиентами использует общий защищённый слой REST/MCP: строгие поля, revision, подтверждение, атомарная история и конфликты без потери черновика. Контактные правки из кабинета участвуют в той же версии. Для обновления Standard нужна миграция 0013 и обновлённые внешние клиенты: [совместимость и ограничения](docs/ADMIN_SECURITY.md).

Приватные файлы: раздел в кабинете/админке, ограниченные загрузки, квоты, скачивание и подтверждаемое удаление через общий API/MCP-сервис. Теперь собственный файл можно выбрать в чате и явно подтвердить передачу консультанту для анализа. Для обновления Standard применяются ожидающие миграции, включая 0015. [Файлы](docs/FILES.md) · [Анализ в чате и границы приватности](docs/CHAT-FILES.md).

## Self-hosted deployment Standard

Для Lite не выполняйте шаги создания D1/R2 ниже — используйте инструкцию [Lite](docs/LITE.md). Старые установки с DB сохраняют Standard; для явного выбора задайте ENGINE_MODE=standard в vars Worker.

1. Создайте базу: `npx wrangler d1 create northstar-db`.
2. Создайте R2 bucket: `npx wrangler r2 bucket create northstar-files`.
3. Скопируйте `wrangler.example.jsonc` в `wrangler.jsonc`, подставьте `database_id` и добавьте binding `FILES` в `r2_buckets`.
4. Примените миграции: `npx wrangler d1 migrations apply northstar-db --remote --config wrangler.jsonc`.
5. Соберите проект: `npm run build`.
6. Разверните Worker: `npx wrangler deploy --config wrangler.jsonc`.
7. До первой регистрации задайте случайный установочный секрет длиной 32–256 символов: `npx wrangler secret put INITIAL_ADMIN_TOKEN --config wrangler.jsonc`. На `/login` в регистрации раскройте «Первичная настройка сайта» и введите этот код. Без секрета создание первого администратора закрыто. Одновременные запросы не создадут двух первых администраторов. Все последующие регистрации создают клиентов; после настройки установочный секрет можно удалить.
8. Добавьте серверные секреты `OPENAI_API_KEY` и/или `XAI_API_KEY` и настройте задачи в `/admin#models`. Не помещайте ключи в публичные настройки или исходный код. Подключение, выбор модели и уровней рассуждения: [docs/AI-PROVIDERS.md](docs/AI-PROVIDERS.md).

В админке настраиваются OpenAI/xAI, модель, рассуждение, лимит токенов, таймаут и совместимая температура. Есть проверка ключа/списка моделей, отдельный платный тест ответа и генератор текстов. До первого сохранения сохраняется прежний OpenAI-маршрут из окружения; затем настройки D1 имеют приоритет над `activeModel`/`OPENAI_MODEL`. Выключенный AI работает в явно обозначенном demo-режиме; отказ включённого провайдера возвращает ошибку без demo-подмены. Успешная пара сообщений сохраняется в D1 одной транзакцией; ошибка БД не выдаётся за успешный ответ. Реальный провайдер в автоматических тестах не вызывается.

## Проверки и безопасное обновление локальной установки

Перед выпуском выполняйте `npm run audit:security`: High/Critical во всём
дереве зависимостей блокируют CI и workflow обновления. Production-аудит
проверяется отдельно через `npm audit --omit=dev`. Оставшиеся Moderate и
причины закреплённых overrides описаны в [DEPENDENCY_SECURITY.md](docs/DEPENDENCY_SECURITY.md).

```bash
npm test
npx tsc --noEmit
npm run lint
npm run build
npm run test:integration
```

Интеграционные тесты поднимают отдельный Worker на свободном порту, применяют все миграции к отдельной D1 и используют отдельное R2-хранилище. Конфигурация — `tests/wrangler.json`, данные — игнорируемые `.test-state-*`. Они не обращаются к порту 8787, основной базе, реальному AI и платежам. Синтетические тестовые хранилища сохраняются для диагностики. На Windows перед пересборкой остановите основной Worker, чтобы он не блокировал файлы `dist`.

Перед обновлением или переносом используйте операционные команды движка:

```bash
npm run db:preflight -- --config wrangler.jsonc --production --env-file .dev.vars
npm run db:backup -- --config wrangler.jsonc --target remote --output backups/site.sql
npm run db:restore -- --config wrangler.jsonc --target remote --file backups/site.sql --confirm-restore RESTORE-REMOTE-D1
```

`db:backup` создаёт SQL и соседний `.manifest.json` с SHA-256 и хешами миграций. `db:restore` не запускается без проверки manifest и точного подтверждения; remote-восстановление потенциально разрушительно, поэтому сначала делайте backup и проверяйте копию на отдельной D1. Подробности: [docs/OPERATIONS.md](docs/OPERATIONS.md). Для текущей версии Wrangler `d1 export --local` не принимает `--persist-to`; этот флаг применяется к local restore/execute.

Для каждого push и Pull Request workflow `.github/workflows/ci.yml` выполняет unit/integration, lint, TypeScript, production build и поднимает локальный Worker для проверки OpenAPI, публичного каталога, health и AI-readable `llms.txt`. Ручной запуск контракта: `npm run check:contract`.

Текущая локальная база этого проекта исторически создана без таблицы учёта миграций. Для неё после проверки схемы применяется **только один раз** дополнительная миграция:

```bash
npx wrangler d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler-state --file drizzle/0003_woozy_bullseye.sql
npm run start
```

Эта команда уже применена к текущей локальной установке. Не повторяйте её и не применяйте заново `0000` к заполненной базе. На новых установках применяйте весь набор через `d1 migrations apply`; на существующих установках с учётом миграций — только ожидающие миграции штатной командой. Перед обновлением production необходимы резервная копия и проверка на копии базы.

### Изменения безопасности и ограничения

- Гостевой диалог требует отдельную HttpOnly-cookie с секретом; знания ID недостаточно. Срок доступа — 7 дней. Старые гостевые диалоги без секрета закрыты для гостей, но не удаляются; администратор сохраняет доступ.
- Новые cookie-сессии хранятся в БД как SHA-256-хеши. Старые сессии совместимы до истечения срока/выхода. Смена пароля отзывает все браузерные сессии пользователя и создаёт новую; API-токены нужно отзывать отдельно.
- Запись в API из другого браузерного origin запрещена. Вход, регистрация, профиль и чат проверяют типы и размеры входных данных. Это не полная валидация всех административных API.
- Атомарные лимиты D1: регистрация 10/час на IP, вход 10/15 минут на IP, чат 30/минуту на пользователя или гостевой IP, профиль 20/15 минут на пользователя. Ответ 429 содержит `Retry-After`. Без доверенного `CF-Connecting-IP` гости делят один локальный лимит; общий NAT тоже может ограничить нескольких клиентов. Нужны дальнейшие антибот-меры и контроль расходов.
- Последние 20 сообщений используются для контекста. Standard сериализует ходы диалога и защищает повтор по Idempotency-Key; потоковой выдачи и инструментов заказа в чате пока нет.
- Внутренние поля не выдаются публичным API каталога, но текстовая инструкция модели не гарантирует защиту от prompt injection. Не храните там секреты, ключи и чувствительные персональные данные.

## Обновления движка из GitHub

Раздел **Админка → Обновления**: выбор/смена репозитория релизов, проверка версии, ручная очередь, автоматические стабильные обновления текущего major и история. По умолчанию выключено. Исполнитель — GitHub Actions в собственном репозитории владельца; Cloudflare-ключи остаются в GitHub Secrets. Первое подключение и правила миграций: [docs/UPDATES.md](docs/UPDATES.md). Локальный адрес недоступен Actions, для установки нужен собственный HTTPS-сайт. Реальный облачный деплой этого механизма пока не проверен.

## Управление через AI-агента

1. Войдите на `/login`. Владелец открывает **Админка → AI-агенты**, клиент — **Кабинет → Доступ AI-агентов**.
2. Выберите права и срок действия (1–365 дней). По умолчанию выдаётся только чтение каталога/заказов; полный доступ владельца требует отдельного подтверждения. Токен показывается один раз, его можно отозвать в этом же разделе.
3. Передавайте его как `Authorization: Bearer nsk_...` в `/api/mcp`, включая initialize. Клиентскому агенту доступны только публичный каталог и собственные заказы в пределах выданных прав.

MCP поддерживает `initialize`, `tools/list` и `tools/call`. Доступны инструменты управления настройками сайта, страницами, ассистентом, клиентами, каталогом, заказами, диалогами и файлами. Публичный контент доступен без авторизации через `/llms.txt`, `/llms-full.txt`, `/api/content?slug=/path` и `/api/products`.

Протокол совместимости — 2025-03-26, stateless HTTP POST с JSON-ответами, без OAuth/SSE. Список инструментов фильтруется по роли и scopes. Команды клиента позволяют оформить собственный заказ, прочитать его историю, отменить ожидающий ручной заказ и запросить checkout. Они не списывают деньги. Ошибки инструмента теперь возвращаются через `result.isError`; проверяйте его наряду с JSON-RPC `error`. Старые токены `*` сохраняются; новые по умолчанию ограничены. [Подключение, scopes и изменения совместимости](docs/MCP.md).

Цена в API хранится в сотых долях валюты: `490000` = `4 900,00 RUB`. Поддержку валют с другим числом десятичных знаков нужно доработать отдельно.

## Заказ от каталога до кабинета

1. В админке откройте **Каталог**: создайте услугу/товар, задайте описание, цену и внутренние инструкции консультанту. В форме цена указывается в основных единицах валюты, в API — в сотых.
2. Публичная карточка доступна по `/catalog/{slug}`. Неактивная карточка возвращает 404. Внутренние инструкции не включаются в её HTML и клиентские данные.
3. Клиент создаёт заказ и попадает на `/account/orders/{id}`. При необходимости вход возвращает на карточку. Деньги при создании заказа не списываются.
4. В кабинете **Заказы** показаны реальные записи; **Бронирования** и **Обращения** пока демонстрационные. В админке **Заказы** доступен общий список.
5. Без платёжного адаптера способ оплаты согласуется отдельно. Клиент может отменить свой ожидающий ручной заказ. Владелец явно подтверждает уже полученную оплату или уже выполненный возврат. Эти кнопки только записывают факт, не переводят деньги.

Цена, валюта и название фиксируются при создании. Изменение каталога не меняет старый заказ. Предложение с заказами нельзя удалить — его можно скрыть. Для заказов старых версий без снимка название отображается как «Заказ из предыдущей версии»; исторические значения не выдумываются.

### Контракт заказов v0.3

- `POST /api/orders`: JSON `productId`, `quantity` (1–99), необязательный `customerNote` (до 2000 символов). Администратор также может указать `customerId`. Обязателен заголовок `Idempotency-Key` из 16–128 букв/цифр/`_`/`-`. Клиент не задаёт сумму, статус или ссылку оплаты.
- Повтор того же запроса с тем же ключом возвращает тот же заказ (200 вместо 201); другой запрос с тем же ключом — 409. Ключ ограничен авторизованным инициатором. Интерфейс сохраняет ключ для повторной отправки неизменённой формы в текущем открытии страницы; восстановление черновика и ключа после перезагрузки страницы пока не реализовано.
- `GET /api/orders`: собственные заказы клиента, все заказы для владельца. `?mine=1` ограничивает результат собственными заказами даже для владельца. Пока максимум 200 записей без пагинации.
- `GET /api/orders/{id}`: заказ и история. Чужой заказ не раскрывается клиенту (404).
- `PATCH /api/orders/{id}`: `status` и текущая `revision`. Допустимы только `pending → paid/cancelled`, `paid → refunded`. Конкурирующая правка возвращает 409. Смена статуса и событие журнала записываются атомарно.
- MCP использует те же функции: `create_order` требует `idempotencyKey`, `get_order` возвращает историю, `update_order` требует `revision`, `checkout_order` получает ссылку оплаты. Клиентский MCP ограничен своими заказами и scopes; браузерный WebMCP работает от текущей cookie-сессии.

### Подключаемая онлайн-оплата

Настройте доверенный HTTPS-адаптер через `PAYMENT_PROVIDER_URL`, его секрет `PAYMENT_PROVIDER_TOKEN` и отдельный `PAYMENT_WEBHOOK_SECRET`. Новые заказы тогда создаются с `paymentProvider=external`. Уже созданные ручные заказы автоматически не переключаются.

После сохранения заказа клиент явно вызывает `POST /api/orders/{id}/checkout` с JSON `{}`. Только эта операция обращается к адаптеру. Запрос содержит `orderId`, `amount`, `currency`, `product` (id/title), `customerId`, а заголовок `Idempotency-Key` равен ID заказа. **Адаптер обязан дедуплицировать этот ключ, включая параллельные запросы.** Ожидается JSON `paymentUrl` с HTTPS-адресом без встроенных логина/пароля. Таймаут — 12 секунд; перенаправления адаптера запрещены. Ошибка оставляет заказ сохранённым и возвращает 502, а не фиктивную ссылку. Повторный запрос с уже сохранённой ссылкой не вызывает адаптер.

Адаптер проверяет подпись и подлинность событий выбранного провайдера и отправляет `POST /api/webhooks/payment` с секретом `x-payment-secret` и JSON:

```json
{
  "eventId": "provider-unique-event-id",
  "orderId": "existing-order-id",
  "status": "paid",
  "amount": 490000,
  "currency": "RUB"
}
```

Поддерживаются `paid`, `cancelled`, `refunded`. Обязательны точные сумма/валюта, существующий внешний заказ и допустимый переход. Последовательные повторы одного события подтверждаются без повторного применения; конфликтующий/запоздалый переход — 409. При конкуренции адаптер должен повторить доставку и сверить статус; возврат клиента на сайт не является подтверждением платежа. Движок доверяет секрету адаптера, а не проверяет подпись конкретного платёжного провайдера сам.

**Совместимость:** старые запросы создания без ключа, изменения статуса без revision и webhook без eventId/amount/currency теперь отклоняются. Обновите свои REST/MCP-клиенты и адаптер перед production-обновлением. Готового адаптера Stripe/ЮKassa и сквозной приёмки настоящих платежей в этой версии нет. Онлайн-отмена, запрос возврата провайдеру, чеки и сверка остаются следующими задачами.

### Оплата бронирований

Платная запись сначала подтверждается в D1 и удерживает выбранный слот 15 минут. `POST /api/bookings/{id}/checkout` использует либо внешний HTTPS-адаптер, либо встроенный Stripe Checkout при `PAYMENT_PROVIDER=stripe`. Для Stripe задайте `STRIPE_SECRET_KEY` и `PUBLIC_SITE_URL`; ссылка создаётся с metadata бронирования и стабильным idempotency key. `POST /api/webhooks/stripe` принимает только события с корректной `Stripe-Signature` и переводит запись в `paid/cancelled/expired`. Полный возврат выполняется owner/admin через `POST /api/bookings/{id}/refund` или MCP `refund_booking`; в Stripe используется PaymentIntent из подтверждённого webhook. Универсальный `/api/webhooks/booking-payment` с `BOOKING_PAYMENT_WEBHOOK_SECRET` также остаётся доступен для других адаптеров. Реальные ключи и sandbox-платежи в этом репозитории не хранятся.

### Миграция коммерческого сценария

Новая миграция `drizzle/0004_clear_tenebrous.sql` добавляет снимок предложения, ключи повторов, версию заказа, журнал событий и индексы. В текущей локальной установке без учёта миграций она применяется отдельно после 0003, один раз:

```bash
npx wrangler d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler-state --file drizzle/0004_clear_tenebrous.sql
```

В текущем рабочем проекте миграция уже применена. Для новых установок используйте весь набор штатных миграций. Исходные данные не удаляются; новые тесты коммерции выполняются только в изолированных `.test-state-*`.
