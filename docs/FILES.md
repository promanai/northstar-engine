# Приватные файлы Standard

Файловый модуль требует D1 binding `DB` и приватный R2 binding `FILES`. Lite остаётся без D1/R2; его временные вложения описаны в [LITE_MEDIA.md](LITE_MEDIA.md). Собственный сохранённый файл теперь можно передать консультанту после отдельного подтверждения: [анализ в чате](CHAT-FILES.md). Сама загрузка AI не вызывает.

## Интерфейс и доступ

Кабинет → «Файлы» (`/account#files`): свои загрузки, расход квоты, скачивание, подтверждаемое удаление и повтор незавершённой операции. Админка → «Файлы» (`/admin#files`): файлы всех пользователей. Новая загрузка принадлежит вошедшему администратору, не выбранному клиенту.

Клиент читает и удаляет только своё; owner/admin — любое. Неизвестные роли запрещены. Cookie-сессии и Bearer-токены используют один сервис; `files:read` и `files:write` выдаются отдельно. Скачивание авторизованное: attachment, application/octet-stream, nosniff, sandbox CSP, private/no-store. Объектные ключи и хеши не выдаются. Не включайте публичный доступ bucket: API не защищает отдельно опубликованные R2-объекты.

## Форматы и квоты

PNG/JPEG/WebP/PDF — от 1 байта до 2 МиБ. TXT/MD — непустой UTF-8 без NUL, до **64 000 байт**. Проверяются расширение, MIME и начальная сигнатура. SVG, HTML, DOC/DOCX и архивы не принимаются. В multipart требуется ровно одно поле `file`; тело ограничено 2 МиБ + 16 КиБ до разбора формы.

Проверка сигнатуры **не является антивирусом или полноценным парсером**. Вредоносное/повреждённое содержимое может иметь корректную сигнатуру. Inline-просмотра нет; безопасность открытия скачанного файла на компьютере не гарантируется. Старые загрузки не перепроверяются задним числом.

Необязательные переменные Worker, положительные целые числа:

| Переменная | По умолчанию |
| --- | ---: |
| FILES_USER_MAX_BYTES | 52428800 (50 МиБ) |
| FILES_SITE_MAX_BYTES | 536870912 (512 МиБ) |
| FILES_USER_MAX_COUNT | 50 |
| FILES_SITE_MAX_COUNT | 2000 |

Ошибочная конфигурация блокирует загрузку с 503. Старые файлы и незавершённые операции учитываются. Превышение новой квоты не удаляет старые данные: блокируются новые загрузки, чтение/удаление остаются доступны. Размер и количество проверяются вместе с резервированием одним SQL statement; конкурирующие запросы не обходят квоту.

30 попыток загрузки и отдельно 30 удалений на пользователя в минуту. Токены делят лимит с браузером; удаления MCP — с REST. Это **не финансовый лимит Cloudflare**: чтение, D1, копии и посторонние объекты R2 не ограничены этими квотами. Удалённые служебные записи пока без автоматической retention-политики.

## API и MCP

- `GET /api/files`: `{files, nextBefore, usage, limits}`, до 50 строк. `all=true` только для администратора. Следующая порция — `before=nextBefore`. Порядок по ID, не дате; это не snapshot при одновременных изменениях.
- `POST /api/files`: multipart `file`, обязательный `Idempotency-Key` (16–100 букв/цифр/дефисов/подчёркиваний). 201 для новой загрузки, 200 для подтверждённого повтора. Ответ `{file, replayed}`.
- `GET /api/files/{id}`: метаданные, включая состояние завершённого удаления.
- `GET /api/files/{id}/download`: байты только для uploaded; 404 при отсутствии содержимого, 409 для незавершённой/удалённой операции.
- `DELETE /api/files/{id}`: JSON `{"confirm":true}`. Содержимое удаляется необратимо, служебная запись остаётся. Повтор по тому же ID допустим.
- MCP: `list_files`, `get_file`, `delete_file`. Агент получает согласие на удаление до confirm:true. Бинарная загрузка — multipart API, скачивание — авторизованный GET по downloadUrl, не base64 в MCP.

После сетевой ошибки сохраняйте **тот же ключ и тот же файл**. Другие содержимое/имя/MIME с прежним ключом — 409. Ключ незавершённой или удалённой операции повторно не используется: проверьте список, закончите удаление при необходимости, создайте новый ключ для новой попытки. В разделе «Файлы» ключ сохраняется при повторе кнопкой, но не после перезагрузки или повторного выбора файла.

Слишком большой запрос возвращает 413; сервер дочитывает только ограниченный запас тела. Произвольно большие/потоковые тела отменяются — клиент может увидеть сетевую ошибку. Клиентская проверка размера нужна для удобства, но не заменяет серверную.

## Частичные отказы

1. D1 резервирует квоту и сохраняет uploading вместе с будущим R2-ключом до записи байтов.
2. После R2.put состояние меняется на uploaded, только если оно всё ещё uploading.
3. При ошибке завершения сервер пытается удалить R2-объект. Неуспешная очистка оставляет учтённую незавершённую операцию.
4. Удаление: deleting → R2.delete → deleted. Квота освобождается после подтверждённого удаления. Сбой позволяет повтор по тому же ID.
5. Обычное удаление защищает uploading первые 15 минут. После этого операцию можно очистить в интерфейсе/API. Автоматического фонового сборщика нет.

D1 и R2 **не образуют общей транзакции**. Прерывание Worker и очень поздняя запись R2 после очистки могут потребовать повтор удаления. Метаданные и ключ остаются для восстановления; автоматическая уборка всех отказов не гарантируется. При спорном результате сервер проверяет D1 и не удаляет уже подтверждённый uploaded-файл.

Удаление не отменяет ранее начатое скачивание и копии у пользователей. D1 backup содержит только метаданные, **не R2-байты**; нужен отдельный R2 backup. Не очищайте служебные записи без проверки R2 и retention-политики.

## Обновление

Аддитивная миграция `drizzle/0012_fantastic_luminals.sql`: nullable request_key/content_hash, уникальный индекс пользователь/ключ и индексы квот. Старые записи сохраняются, объекты не переименовываются.

Перед релизом Standard проверьте backup и точную цель D1/R2, примените ожидающие миграции по [OPERATIONS.md](OPERATIONS.md). В этой доработке миграция применена **только в изолированных тестовых базах**; рабочая локальная и облачная базы не изменены. Lite миграция не нужна.

Изменения контракта: раньше POST допускал произвольные типы до 10 МиБ без ключа; теперь строгий формат и обязательный ключ. MCP list_files возвращает объект со списком/курсором и по умолчанию только свои файлы, а не массив всех файлов сайта. Обновите внешние клиенты перед релизом.

## Проверки и ограничения

Модульные тесты: форматы, UTF-8, имена, квоты, права. Интеграционные: изолированный локальный Worker с D1/R2, чужие файлы, параллельные квоты/повторы, скачивание, MCP/API, искусственные отказы завершения записи/удаления D1, фактическая компенсация R2, очистка старой операции. Lite проверяет отключение всех новых endpoints без хранилища.

Облачный R2/D1, обрыв Worker во всех точках операции, сетевой отказ R2, большие нагрузки и визуальная приёмка нового интерфейса ещё не проверены. Привязка файлов к сообщениям и передача AI реализованы в отдельном шаге (миграция 0015). Следующие задачи: антивирусный карантин при необходимости бизнеса, фоновые сверка/очистка, retention и R2 backup.
