# Доступ AI-агентов к установленному сайту

В кабинете откройте **Доступ AI-агентов**, в админке — **AI-агенты**. Укажите название, срок 1–365 дней и разрешения. По умолчанию новый токен позволяет только читать каталог и заказы. Секрет показывается один раз; в D1 хранится SHA-256, не исходный токен. Можно посмотреть дату последнего обращения и отозвать собственный токен. Старые бессрочные токены не удаляются автоматически — рекомендуется перевыпустить их с ограниченным сроком и правами.

## Подключение

- Endpoint: `https://ВАШ-ДОМЕН/api/mcp`.
- Транспорт: HTTP POST, JSON-RPC 2.0, ответы JSON, версия протокола **2025-03-26**.
- Заголовки: `Content-Type: application/json`, `Authorization: Bearer ВАШ_ТОКЕН`.
- Поддерживаются `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`.
- Авторизация обязательна уже на initialize. Уведомление initialized получает 202. GET получает 405: сервер не открывает SSE-поток.
- Это подключение вручную выданным токеном, не OAuth. Нужен MCP-клиент, поддерживающий произвольный Bearer header. Совместимость с конкретными внешними клиентами и новыми версиями MCP пока не подтверждена.
- В production обязателен HTTPS. Локальный адрес доступен только на той же машине. Не передавайте cookie браузера агенту.

Запросы:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-03-26",
    "capabilities": {},
    "clientInfo": { "name": "my-agent", "version": "1.0" }
  }
}
```

```json
{ "jsonrpc": "2.0", "method": "notifications/initialized" }
```

```json
{ "jsonrpc": "2.0", "id": 2, "method": "tools/list" }
```

## Агент клиента

Для собственных файлов также доступны `files:read` (`list_files`, `get_file`, скачивание через API) и `files:write` (multipart-загрузка через API, `delete_file` с подтверждением). По умолчанию эти права не выдаются. `list_files` возвращает `{files, nextBefore, usage, limits}`; `all:true` разрешено только owner/admin. Квоты, повтор запросов и изменения контракта: [FILES.md](FILES.md).

Разрешения доступны независимо друг от друга:

| Scope            | Возможности                    | Ограничения                                                         |
| ---------------- | ------------------------------ | ------------------------------------------------------------------- |
| `catalog:read`   | `list_products`                | Только активный публичный каталог, без внутренних инструкций        |
| `orders:read`    | `list_orders`, `get_order`     | Только заказы своего аккаунта                                       |
| `orders:write`   | `create_order`, `update_order` | Создание своего заказа, отмена своего ожидающего ручного заказа     |
| `checkout:write` | `checkout_order`               | Получение ссылки для собственного заказа через подключённый адаптер |

Агент клиента не может управлять сайтом, получить клиентов/диалоги/черновики, оформить заказ за другого клиента, объявить заказ оплаченным или оформить возврат денег. `tools/list` показывает только разрешённые инструменты и клиентские параметры. Те же права проверяются при вызове, независимо от полученного списка.

Последовательность: получить каталог → согласовать товар/количество с клиентом → создать заказ → прочитать его итоговую сумму → с согласия клиента запросить checkout → передать ссылку клиенту → проверить статус заказа. Сумма определяется сервером. Заказ не является платежом; checkout не списывает деньги и не подтверждает оплату. Без адаптера возвращается явная ошибка, а заказ сохраняется. Статус платежа обновляется только через существующую проверку платёжных событий или подтверждение владельцем уже полученного ручного платежа.

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "create_order",
    "arguments": {
      "productId": "ID_ИЗ_КАТАЛОГА",
      "quantity": 1,
      "idempotencyKey": "unique-request-key-0001",
      "customerNote": "Комментарий клиента"
    }
  }
}
```

При повторе того же заказа сохраняйте `idempotencyKey`; для нового намерения используйте новый ключ. Успешный ответ содержит `result.structuredContent.order`. `get_order` возвращает заказ и события; `checkout_order` — `{order}`, где ссылка находится в `order.paymentUrl`. Нельзя считать возвращение клиента со страницы провайдера подтверждением платежа.

Для отмены прочитайте текущую revision через get_order и вызовите update_order с `id`, `status: "cancelled"`, `revision`. Отмена внешней платёжной сессии и фактический возврат остаются задачами интеграции с провайдером.

## Агент владельца

Обновлённые инструменты ассистента/клиентов требуют подтверждения и текущей версии; добавлены assistant_history, restore_assistant, get_customer, customer_history. Инструмент записи без соответствующего read-scope возвращает только подтверждение версии (для существующего клиента — id/revision), а не приватный полный объект. Старые формы ответов и изменение activeModel через update_assistant больше не поддерживаются. [Полный контракт и порядок перехода](ADMIN_SECURITY.md).

Для записи на услуги клиенту дополнительно доступны `bookings:read` (`list_booking_slots`, `list_bookings`, `get_booking`) и `bookings:write` (`create_booking`, `checkout_booking`, `update_booking`). Только собственные записи, будущий перенос/отмена; завершение услуги и изменение расписания запрещены. Создание требует `idempotencyKey`, изменение — `revision`. Бесплатная услуга подтверждается сразу, платная удерживает слот на 15 минут; `checkout_booking` только получает ссылку, а подтверждение оплаты приходит отдельным проверенным webhook. Полная инструкция и изменение старого контракта — [BOOKINGS.md](BOOKINGS.md).

Владелец выбирает отдельные read/write-права для настроек, страниц, ассистента, клиентов, каталога, заказов, бронирований и интеграций; отдельное чтение диалогов/файлов. `site_get` требует сразу `site:read`, `assistant:read`, `pages:read`, `catalog:read`, поскольку объединяет эти данные. Полный `*` разрешён только владельцу/администратору после явного подтверждения. У владельца `orders:read` открывает все заказы сайта; у клиента — только его собственные.

Для расписания владельцу доступны `list_booking_schedule` и `manage_booking_schedule`, с ролью owner/admin и scopes `bookings:read` / `bookings:write`. Свободная запись дат/статусов через прежний `update_booking` больше не поддерживается: это обходило защиту от двойной записи.

Управление клиентами не даёт права менять аккаунт администратора. Управление токенами и источником обновлений остаётся в браузерной сессии владельца: даже полный MCP-токен не создаёт другие токены и не меняет цепочку обновления кода.

Ограничения scopes проверяются также в существующих REST-обработчиках, использующих Bearer-аутентификацию. Публичные GET могут возвращать публичную часть без авторизации; cookie-only API не становятся доступными агенту. Присутствие Authorization запрещает наследовать права параллельно переданной браузерной cookie. Поэтому отозванный или ограниченный токен нельзя «дополнить» полномочиями браузера.

## API токенов

- `GET /api/tokens`: только свои метаданные, `allowedScopes`, `owner`; cookie-сессия.
- `POST /api/tokens`: `name`, `expiresInDays` (по умолчанию 30), `scopes` (по умолчанию catalog:read/orders:read). Для `*` дополнительно `confirmFullAccess: true`, только владелец. Создание ограничено 10 запросами/час на аккаунт.
- `DELETE /api/tokens?id=...`: собственный токен, cookie-сессия и Content-Type application/json. Отзыв действует на следующие запросы, но не прерывает уже выполняющуюся операцию и не отменяет созданные заказы.

Полные контракты этих endpoints доступны в `/api/openapi`. В этой итерации схема D1 не менялась: используются существующие поля api_tokens. Автоматической миграции старых `*` в новые scopes нет, поэтому проверьте старые выдачи вручную.

## Ошибки и совместимость

Изменение относительно предыдущего MVP: initialize теперь требует аутентификации; ошибки выполнения инструментов передаются в `result.isError: true` и `result.content`, а ошибки протокола/доступности инструмента — в JSON-RPC `error`. Клиент должен проверять оба случая. Не ориентируйтесь только на HTTP 200. Без id команды не выполняются. Лимит MCP — 120 запросов/минуту на пользователя, плюс лимиты существующих операций заказов.

Проверяются размер JSON, origin, обязательные поля, неизвестные верхнеуровневые поля, базовые типы/enum/границы. Это не полная рекурсивная JSON Schema-валидация старых административных объектов. Их бизнес-валидацию и единый журнал всех действий нужно доработать отдельно.

Локальные тесты проверяют выпуск/хеширование/отзыв/истечение токенов, scopes, MCP-discovery, изоляцию клиентов, повторы заказов и запрет фиктивного платежа. Настоящие платежи и соединение с внешним MCP-клиентом не выполнялись.

Основа контракта: [MCP tools 2025-03-26](https://modelcontextprotocol.io/specification/2025-03-26/server/tools) и [Streamable HTTP 2025-03-26](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports). Это выбранная версия совместимости, не заявление о поддержке последней версии спецификации.
