# Защищённое управление ассистентом и клиентами

Этот этап относится к Standard. Lite остаётся без D1, кабинета и административных API.

## Ассистент

Редактор поддерживает имя, язык, инструкции, включение/отключение, историю и восстановление. Чат читает ту же конфигурацию, что REST/MCP. Сохранение и восстановление применяются сразу; восстановление включает **все** поля и может включить отключённого консультанта.

- Публичный `GET /api/assistant` всегда возвращает только name/defaultLocale/status, даже при наличии административной сессии.
- `GET /api/assistant?view=admin` требует assistant:read и возвращает `{assistant:{name,systemPrompt,defaultLocale,status,revision}}`.
- `GET /api/assistant?view=history&before=...` требует assistant:read: до 50 событий, revision по убыванию. before необязателен; это номер версии.
- `PUT /api/assistant`: частичное изменение полей, обязательные revision и confirm:true. Имя 1–120 символов, инструкции до 16000, язык до 35 в формате ru/en/pt-BR, status — active или disabled.
- Восстановление: тот же PUT с `{revision,targetRevision,confirm:true}`, требует одновременно assistant:read и assistant:write.
- MCP: get_assistant, update_assistant, assistant_history, restore_assistant; общий сервис с REST.
- Без assistant:read успешная запись возвращает **только revision**, не остальные приватные поля.
- activeModel и произвольные поля не принимаются. Модели/ключи — отдельный существующий раздел «Модели» и session-only `/api/ai`; этот этап не добавляет управление провайдерами через MCP.
- Общий лимит REST/MCP — 20 записей в минуту на пользователя.

При первом управляемом сохранении текущий legacy-профиль становится базовой версией документа assistant-profile в site_documents; последующие версии и атрибуция хранятся в site_document_revisions. Изменение и событие выполняются одним D1 batch с проверкой revision. Ошибка истории откатывает изменение. Параллельное первое сохранение создаёт только одну новую версию.

Старые assistant_profiles/assistant_prompt_versions не удаляются и не переписываются. Старые prompt-логи не смешиваются с новой историей; автоматически восстановить их из нового редактора нельзя. До первой записи используется legacy-профиль. После неё для бизнес-контекста авторитетен новый документ. Legacy active_model ещё может участвовать в прежнем fallback настройки моделей до явного сохранения /api/ai.

## Клиенты

Административный редактор поддерживает создание контактной карточки, редактирование, историю и подтверждаемое удаление. Создание в UI не назначает пароль и не отправляет приглашение. Неизвестные роли, аккаунты owner/admin, поля role/passwordHash/mutationId не доступны через CRUD клиентов.

- `GET /api/customers`: customers:read; `{customers,nextBefore}`, до 100 записей, ID по убыванию. before — курсор ID; это не сортировка по дате и не snapshot.
- `POST /api/customers`: customers:write, email и confirm:true; optional firstName/lastName/phone/password. Начальный пароль только при создании, 8–256 символов.
- `GET /api/customers/{id}`: customers:read; контактная карточка с revision.
- `PATCH /api/customers/{id}`: customers:write, revision, confirm:true и хотя бы одно контактное поле. Email нормализуется в lowercase, длина до 254; имя/фамилия до 120, телефон до 40. Пустая строка очищает необязательное поле. null/вложенные объекты вместо строк отклоняются.
- `DELETE /api/customers/{id}`: customers:write, текущая revision и confirm:true.
- `GET /api/customers/{id}/history`: customers:read, необязательный before (revision); 50 событий с контактными снимками, источником и автором. Пароли, хеши и токены в снимки не включаются.
- MCP: list_customers, get_customer, create_customer, update_customer, delete_customer, customer_history.
- Без customers:read успешное **изменение существующей** карточки возвращает только id/revision. Создание возвращает созданную карточку без секретов.
- Общий лимит записей REST/MCP — 30 в минуту на пользователя.

При смене email администратором сессии и токены клиента отзываются в той же транзакции. Входящие уже выполняющиеся операции отзывом не отменяются. Смена пароля/роли администратором через этот CRUD не поддерживается.

Удаление удаляет контакт и отзывает сессии/токены, но **не каскадирует бизнес-данные**. Заказы, бронирования, диалоги, файловые метаданные и другие FK-связи блокируют операцию с 409; откатываются также отзыв доступа и событие удаления. Даже исторические/удалённые файловые метаданные могут удерживать связь. Политика архивирования/анонимизации таких клиентов — отдельная задача.

История контакта переживает успешное удаление. Это **не полное стирание персональных данных**. Автоматической retention-политики и восстановления удалённой карточки из истории нет; доступ к журналу только административный.

Создание не имеет отдельного idempotency key: уникальный email предотвращает повтор идентичной карточки, но после неопределённого сетевого результата нужно прочитать список. Повтор удаления возвращает 404; результат можно уточнить по истории. Конфликт версии — 409, ошибка хранилища — 503, а не фиктивная ошибка дубликата.

## Личный кабинет и конкурирующие правки

`GET /api/auth/me` теперь возвращает revision; `PATCH /api/auth/me` **требует её**. Форма кабинета передаёт загруженную версию. Самостоятельные контактные/парольные изменения увеличивают ту же users.revision, что административные. Для customer появляется безопасный контактный снимок с source=profile, без пароля/хеша; административные аккаунты не записываются в клиентский журнал.

При конфликте редакторы оставляют черновик и предлагают сравнить с серверными данными. Кнопка замены черновика явно отбрасывает локальные правки; автоматического слияния и сохранения черновика после перезагрузки нет.

Существующая смена пароля проверяет текущий пароль и отзывает браузерные сессии. Полный пересмотр authentication/recovery/MFA и политики отзыва API-токенов при самостоятельной смене пароля в этот этап не входит.

## Обновление установки

Аддитивная миграция `drizzle/0013_common_magma.sql` добавляет users.revision (default 0), users.mutation_id и customer_revisions с уникальным индексом контакт/версия. Данные не удаляются, старые миграции не изменены. Миграция применена только в изолированных тестовых базах; рабочая локальная и облачная D1 не изменялись.

Для Standard: backup, окно без записей, ожидающие миграции, новая версия Worker, обновление браузерных страниц и внешних клиентов, проверка входа/CRUD/MCP. Не эксплуатируйте старый Worker параллельно с новым: прежние обработчики не участвуют в новом протоколе версий. Lite миграция не нужна. Общий порядок — [OPERATIONS.md](OPERATIONS.md).

Изменения несовместимого контракта:

1. Записи ассистента/клиентов требуют confirm:true; обновление/удаление — revision.
2. PATCH собственного профиля требует revision.
3. Приватный профиль ассистента читается только с view=admin; MCP get_assistant возвращает {assistant}.
4. MCP list_customers возвращает {customers,nextBefore}, create/update — {customer}, а не голую карточку/массив.
5. Токен с одним write-scope не получает приватный полный объект в ответе на обновление.
6. activeModel перемещён из административного профиля в отдельную настройку /api/ai; старые запросы с этим полем отклоняются.

## Границы проверки

Тесты: строгие типы/границы, scopes, отсутствие приватных полей, параллельные записи и начальная версия, восстановление ассистента, отключение чата, отказы D1-журнала, совместная версия кабинета и CRUD, отзыв сессий/токенов при смене email, откат удаления связанного клиента, история после удаления и контракты API. Тесты выполняются на отдельном локальном Worker/D1/R2; не используют реальные аккаунты, платные вызовы или production-данные.

Не проверены облачный rollout, визуальная/мобильная приёмка новых редакторов, внешние MCP-клиенты и нагрузочные пределы. Не реализованы общий бюджет AI, встроенный AI-администратор, MFA/recovery, полноценная политика персональных данных или единый журнал **всех** административных модулей.
