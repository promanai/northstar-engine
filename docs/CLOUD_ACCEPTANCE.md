# Приёмка Standard в Cloudflare

## Автоматическая HTTP-проверка без изменения бизнес-данных

В движке есть отдельная команда для уже развёрнутого Standard. Она не выбирает аккаунт, не создаёт ресурсы и не разворачивает код. Выберите **свой точный HTTPS-адрес**. Каталог отчётов должен существовать; каждый запуск требует нового файла.

```bash
npm run check:standard -- --url https://YOUR-SITE.example --report outputs/standard-before.json
```

Проверяются 11 фиксированных GET-запросов: health, контракт Standard с новыми разделами, HTML главной, публичный каталог без внутренних полей, Markdown, ссылки для агентов и запрет анонимного доступа к профилю, обзору, обращениям, диалогам и файлам. Ответ Lite не считается успехом Standard. Ошибка, редирект, неподходящий тип ответа и ответ более 1 MiB приводят к провалу соответствующей проверки. Таймаут запроса — 10 секунд, автоматических повторов нет.

Это **HTTP smoke**, а не полная облачная приёмка. PASS без сессии означает только публичные проверки; административные проверки в отчёте будут `skipped`. Команда возвращает ненулевой exit code при провале. Cloudflare Access, login redirect, защита от ботов и недоступность сети не обходятся и не маскируются как успех.

### Проверка ожидаемой сборки после обновления

Сохраните `dist/engine-build.json` вместе с конкретной сборкой до следующего запуска build. Передайте именно паспорт ожидаемого выпуска:

```bash
npm run check:standard -- --url https://YOUR-SITE.example --expect-build dist/engine-build.json --report outputs/standard-after-update.json
```

Health обязан вернуть тот же идентификатор, версию и commit с `Cache-Control: no-store`. Несовпадение, старый Worker без паспорта или неправильный паспорт завершают проверку ошибкой **до отправки сессии**. В отчёте `release.status` будет `matched`, `mismatch`, `not_verified` (проверка не дошла до сравнения) или `not_requested` (флаг не передан). PASS без флага не подтверждает версию. [Формат и границы паспорта](BUILD_IDENTITY.md): это сверка метки сборки, не цифровая подпись или аттестация байтов развёрнутого Worker.

## Дополнительные проверки администратора

Войдите на **этой же тестовой установке** самостоятельно. Передайте её действующую сессию через переменную окружения `NORTHSTAR_SMOKE_COOKIE` в формате `northstar_session=...` безопасным способом (например, через секрет окружения CI). Не передавайте пароль, cookie в аргументе команды, чате, репозитории или скриншоте. Скрипт не читает `.env` и не выполняет вход за пользователя.

```bash
npm run check:standard -- --url https://YOUR-SITE.example --admin-origin https://YOUR-SITE.example --report outputs/standard-admin.json
```

`--admin-origin` должен в точности совпадать с origin назначения. Секрет без явного origin, несовпадение адресов или неправильный формат cookie блокируют весь запуск до сети. После проверки удалите переменную из окружения; при необходимости завершите тестовую сессию на сайте.

С сессией выполняются ещё 4 GET-запроса: роль администратора и запрет кеширования профиля, корректный обзор за 24 часа, запрет чужого Origin и запрет fallback с ошибочного bearer-токена на административную cookie. Тексты обращений, контакты, cookie, заголовки ответа и сырые сетевые ошибки в отчёт не записываются. Отчёт содержит целевой origin, время, количество запросов, названия проверок и ограниченные коды ошибок. Сам origin может быть чувствительным — выбирайте, кому передавать отчёт.

Секрет не отправляется до успешной проверки health и контракта Standard. Это дополнительная защита от случайной ошибки, **не доказательство доверенности сервера**: владелец обязан проверить адрес. Редиректы не выполняются, полученные cookies не принимаются, вызовов на сторонние адреса нет. DNS/TLS используются штатно; инструмент не является изолированной сетевой песочницей.

GET не означает нулевой расход: возможны Worker/D1-чтения, серверные логи и изменения счётчика квоты обзора. Скрипт не отправляет сообщения, не вызывает AI/голос/платежи, не создаёт пользователей и не меняет бизнес-записи. Не запускайте его в цикле.

## Полный порядок облачной приёмки

- [ ] Явно выбрать аккаунт владельца и отдельные тестовые Worker, D1, R2 и HTTPS-адрес. Не использовать рабочие binding/домены.
- [ ] Пройти [production preflight](OPERATIONS.md), создать ресурсы, применить миграции и развернуть конкретный выпуск. Секрет bootstrap задаёт владелец; платные провайдеры в тесте выключены.
- [ ] Выполнить публичный smoke, войти через браузер и выполнить административный smoke. Сохранить отчёты отдельно для каждой стадии.
- [ ] Проверить создание клиента, demo-диалог, обращение и загрузку файла на тестовых данных. Проверить мобильный интерфейс, чужой доступ и скачивание собственного файла.
- [ ] Остановить запись и выполнить remote D1 backup. Восстановить копию **в другую пустую тестовую D1**, сверить данные и миграции. Никогда не выполнять restore в источник ради проверки.
- [ ] Проверить обновление между двумя точно выбранными версиями, сохранность данных и повторить smoke с `--expect-build` после обновления/восстановления. Сверка метки не заменяет проверку миграций, данных и артефакта развёртывания.
- [ ] Проверить настоящий Cron Trigger, логи и обработку ошибок. Затем отдельно отработать согласованный D1/R2 backup: SQL не содержит файлы.
- [ ] Реальные AI, голос, оплата и возврат проверяются отдельно с разрешением владельца на внешние операции.
- [ ] После сохранения доказательств перечислить точные созданные ресурсы и согласовать удаление. Подтвердить отсутствие каждого удалённого ресурса; скрипт ничего автоматически не удаляет.

Эти пункты пока не отмечены выполненными в облаке. Автоматического provisioning, upgrade/rollback, remote restore или удаления ресурсов в `check:standard` нет. Для них используются существующие команды и явное решение оператора по [инструкции эксплуатации](OPERATIONS.md).

## Локальная проверка самого инструмента

`npm test` проверяет политику адресов/секретов, ожидаемую сборку, редиректы, отказы, ограничения тела, отсутствие утечек в отчёт и запрет перезаписи. `npm run test:acceptance` запускает тот же набор на собранном Worker с изолированной D1 и синтетической сессией, сверяет паспорт и неизменность бизнес-таблиц. `npm run test:lite` также сверяет паспорт собранного Lite. CI сохраняет JSON-отчёты и паспорт сборки, без дампов базы.

Для уже запущенного **тестового Standard** на loopback допустим явный `--allow-local`:

```bash
npm run check:standard -- --url http://127.0.0.1:8789 --allow-local --report outputs/standard-local.json
```

Флаг разрешает HTTP только для `127.0.0.1`, `localhost` и `[::1]`. Проверка локального Lite намеренно завершается провалом Standard; переключать рабочий режим ради неё не нужно.
