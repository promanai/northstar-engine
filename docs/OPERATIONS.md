# Эксплуатация self-hosted установки

Команды ниже запускаются из корня репозитория клиента. Они не передают ключи AI/платежей в D1 и не печатают значения секретов.

## Preflight перед релизом

Проверка не обращается к Cloudflare и ничего не меняет:

```bash
npm run db:preflight -- --config wrangler.jsonc
npm run db:preflight -- --config wrangler.jsonc --production --env-file .dev.vars
npm run db:preflight -- --config wrangler.jsonc --format json
```

Проверяются Worker entrypoint, assets, D1 binding `DB`, production D1 ID, R2 `FILES`, каталог миграций, уникальность номеров, `engine-release.json` и платёжные параметры. В обычном режиме незаполненные production-поля — предупреждения; с `--production` они становятся ошибками. Для Stripe нужны `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` и HTTPS `PUBLIC_SITE_URL`.

## Backup

```bash
npm run db:backup -- --config wrangler.jsonc --target remote --output backups/site-2026-09-09.sql
```

Для локального сервиса, запущенного через `npm run start`:

```bash
npm run db:backup -- --config wrangler.jsonc --target local --persist-to .wrangler-state --output backups/local.sql
```

Рядом с SQL создаётся `*.sql.manifest.json`. В нём фиксируются размер, SHA-256, база, цель, версия формата и хеши всех SQL-миграций. Существующие файлы не перезаписываются без `--overwrite`. Wrangler сам подтверждает remote/local export только через переданный скриптом безопасный `--skip-confirmation`: export не меняет базу.

Локальные backup и restore требуют явного `--persist-to`: каталог больше не выбирается автоматически. Для стандартного состояния обычного `wrangler dev` укажите `<каталог-config>/.wrangler/state`; для `npm run start` — `.wrangler-state`. Binding/ID в config должны соответствовать выбранному состоянию. Отсутствующий каталог или пустая база приводят к ошибке, а не к успешной пустой копии.

У установленного Wrangler команда `d1 export` не поддерживает `--persist-to`. Локальный экспорт использует тот же механизм `miniflare_d1_export` через поставляемый с Wrangler Miniflare, направляя его строго в выбранный каталог. Remote export остаётся штатной командой Wrangler. Перед копированием остановите запись: экспорт не является согласованной копией одновременно меняющихся D1 и R2. SQL содержит личные данные и хеши учётных данных — храните его как секрет, вне публичного репозитория. R2-объекты в SQL не входят.

Локальный SQL сначала создаёт все таблицы и индексы, затем вставляет данные. Это устраняет обнаруженный на чистом восстановлении сбой `no such table: main.users`, когда дочерняя запись импортировалась до создания родительской таблицы. Отложенная проверка связей не заменяет наличие таблиц; [правила внешних ключей D1](https://developers.cloudflare.com/d1/sql-api/foreign-keys/). Старые или remote-дампы обязательно проверяйте восстановлением на отдельной базе: локальное исправление не переписывает существующие копии.

## Restore

Восстановление выполняет SQL через `wrangler d1 execute --file` после проверки manifest, размера, SHA-256 и набора миграций:

```bash
# только после проверки на копии
npm run db:restore -- --config wrangler.jsonc --target remote \
  --file backups/site-2026-09-09.sql \
  --confirm-restore RESTORE-REMOTE-D1
```

Для локальной изолированной D1 можно указать state directory:

```bash
npm run db:restore -- --config wrangler.jsonc --target local \
  --persist-to .wrangler-restore-check \
  --file backups/site-2026-09-09.sql \
  --confirm-restore RESTORE-LOCAL-D1
```

Точное подтверждение различается для local и remote, чтобы локальная команда не могла быть незаметно перенесена в production. Изменение миграций между backup и restore блокирует операцию; `--allow-migration-drift` допускается только после ручной проверки совместимости. Для существующей непустой базы сначала сделайте отдельную копию и отработайте восстановление на новой D1: SQL export может содержать схему, индексы и данные.

Повреждённый или отсутствующий список хешей миграций блокируется даже с `--allow-migration-drift`. Manifest защищает от случайного повреждения, но не является цифровой подписью: SQL и manifest должны поступать из доверенного источника.

## Воспроизводимая локальная приёмка Standard

```bash
npm run build
npm run test:acceptance
```

Сценарий создаёт отдельные исходную и восстановленную базы в новом `.test-state-acceptance-*`, применяет реальные миграции и использует собранный Worker. Проверяет регистрацию и вход, диалог demo AI, обращение и ответ администратора, согласие и отчёты аналитики, запрет чужого доступа. Затем вызывает настоящие `db:backup`/`db:restore`, сверяет строки всех таблиц, структуру и журнал миграций, повторно применяет миграции и входит в восстановленный сайт. Отсутствие подтверждения и повреждение SQL должны блокировать восстановление до записи.

`acceptance-report.json` содержит только результаты проверок, номера миграций, количества строк и размеры — без паролей, cookie, текстов сообщений и дампов. Локальные SQL и тестовое состояние сохраняются для диагностики; CI публикует только JSON-отчёт. Внешние запросы Worker блокируются. Рабочий сайт, его база и Cloudflare не затрагиваются.

Это сквозная **HTTP/D1-приёмка**, не проверка браузерной вёрстки, нагрузки, R2 backup или реальных оплат/AI. Она не заменяет облачную приёмку владельцем.

## Порядок обновления

1. Остановите запись или выберите окно обслуживания.
2. Выполните production-preflight и сохраните JSON-отчёт.
3. Создайте remote backup и сохраните SQL вместе с manifest вне репозитория.
4. Проверьте backup на отдельной D1.
5. Примените только ожидающие аддитивные миграции, затем разверните Worker.
6. Проверьте `/api/health`, публичную главную, вход, `/api/openapi` и MCP discovery.
7. При ошибке не запускайте миграции повторно вслепую: сохраните логи, проверьте `d1_migrations` и используйте аварийный runbook владельца.

Эти команды не являются автоматическим rollback: backup/restore и миграции требуют решения оператора. Remote backup/restore, чистая установка и реальный cloud update должны быть проверены в аккаунте клиента до production.
