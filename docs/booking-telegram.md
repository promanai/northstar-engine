# Запись пациента и Telegram

Standard / D1. Lite остаётся без базы и без записей. Рабочий кабинет OraVera: `/account`; расписание и уведомления: `/admin#bookings`.

## Подключение клиники

- [ ] Заполнить реальные услуги, стоимость, ресурсы/врачей и слоты через админку. Тестовые данные не создаются в рабочей базе.
- [ ] Применить новую миграцию `0020_fat_reavers.sql` вместе с остальными миграциями перед запуском новой версии. Сначала сделать резервную копию и проверить на отдельном окружении.
- [ ] Создать бота через [BotFather](https://t.me/BotFather), добавить его в приватную группу клиники или начать личный диалог с ним.
- [ ] Сохранить `TELEGRAM_BOT_TOKEN` и числовой `TELEGRAM_CHAT_ID` в Worker secrets нужного клиентского проекта. Не использовать публичный канал, не публиковать токен и не передавать его в контекст AI. Локально секреты задаются в `.oravera-standard-local/.env`, который не должен публиковаться.
- [ ] Установить `PUBLIC_SITE_URL` в реальный HTTPS origin сайта без пути, параметров и логина/пароля. Значение `https://example.com` не принимается.
- [ ] После согласования адресата установить `BOOKING_TELEGRAM_ENABLED=true`. До этого сообщения не отправляются, а новые события сохраняются в очереди. При включении накопленная очередь будет обработана; исторические события до миграции не рассылаются.
- [ ] Добавить Cron `*/5 * * * *` для повторной обработки очереди. Он включён в Standard-шаблон конфигурации, но существующие облачные установки нужно обновить отдельно. Локальный Wrangler не запускает Cron автоматически.
- [ ] Создать одну согласованную тестовую запись, проверить сообщение в нужном чате и статус в админке. Удалять или отменять её только по согласованному сценарию.

## Что получает Telegram

Только тип события, непрозрачный номер записи, номер события, версия и ссылка на защищённую админку. Не передаются ФИО, email, телефон, услуга, врач, комментарий, время приёма или фото. Предпросмотр ссылок отключён; платные рассылки запрещены. Номер записи всё равно относится к операционным метаданным — клиника должна согласовать этот канал. Это не заявление о медицинском или юридическом соответствии.

Используется фиксированный [Telegram Bot API sendMessage](https://core.telegram.org/bots/api#sendmessage). Перенаправления не выполняются. Адресат и токен не принимаются из пользовательского запроса, страницы или MCP.

## Надёжность и ограничения

- Триггер D1 создаёт элемент очереди в той же транзакции, что и событие записи. Откат записи откатывает уведомление.
- Создание, перенос, отмена и проверенные платёжные события используют общий журнал, независимо от REST/MCP. После изменения выполняется фоновая попытка обработки; Cron и кнопка в админке обрабатывают оставшееся.
- Одна обработка забирает до трёх элементов с атомарной блокировкой. Подтверждённый rate limit Telegram допускает до пяти автоматических попыток с задержкой не менее 60 секунд.
- `sent` означает, что API Telegram вернул ID сообщения, а не что человек прочитал его.
- Таймаут, некорректный ответ или прерванный Worker дают `uncertain`. Автоматического повтора нет: у `sendMessage` нет ключа идемпотентности. Администратор проверяет чат и отдельно подтверждает риск дубликата перед повтором.
- Лента доступна администратору за 24 часа / 7 / 30 дней, по 50 событий с курсором; обновляется кнопкой. Смена получателя не разделяет старую очередь по адресатам — обработайте её перед сменой секретов.
- Email/SMS пациенту, чтение ответов из Telegram, подтверждение записи кнопкой в боте и автоматические напоминания перед приёмом не реализованы.

## REST / MCP

- Пациент использует `/api/booking-slots`, `/api/bookings` и `/api/bookings/{id}`; MCP — `list_booking_slots`, `create_booking`, `get_booking`, `update_booking`.
- `create_booking` и REST принимают `expectedPrice`, `expectedCurrency`, `expectedSlotRevision` вместе: сервер атомарно проверяет предложенную цену/валюту/версию. Старые клиенты без этих полей совместимы; для нового агента передавать их рекомендуется всегда.
- UI показывает подтверждение до записи. Это не криптографическое доказательство согласия для внешнего агента: универсальный серверный prepare/confirm протокол ещё не реализован.
- После неопределённого результата создания повторить тот же payload с тем же `Idempotency-Key` / `idempotencyKey`. Перенос и отмена требуют последнюю `revision`; при конфликте заново прочитать запись.
- Платная запись с `paymentStatus=pending` — удержание на 15 минут, не окончательное подтверждение. Checkout выполняется отдельно, оплата подтверждается только проверенным webhook. Отмена не выполняет возврат автоматически.
- Приватная лента: `GET /api/booking-activity`, для владельца MCP `list_booking_activity` с `bookings:read`. Пациенту лента недоступна. Отправка/повтор через POST — только сессия администратора, подтверждение и same-origin JSON, без Bearer.

## Проверки

`npm run test:oravera-account` — настоящий локальный кабинет, D1, REST/MCP, потерянный ответ, отмена/перенос и мобильные размеры.

`npm run test:booking-notifications` — собранный Worker и отдельная D1; отправки Telegram и оплаты перехватываются локально. Проверяются очередь, откат, перезапуск, конкуренция, ошибки, приватность и запрет редиректов. Реальных сообщений или платежей эти тесты не выполняют.
