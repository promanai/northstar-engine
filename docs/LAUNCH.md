# Паспорт запуска сайта для владельца и AI-агента

Этот паспорт поставляется вместе с движком. Он помогает превратить установку в конкретный клиентский сайт: выяснить замысел, согласовать материалы и поведение ассистента, выполнить работы и принять результат. Открытый адрес Worker — только один из этапов.

Начните с [полного списка вопросов и графа](LAUNCH_CHECKLIST.md). Источник — `onboarding/checklist.json`: 24 шага, конкретные вопросы, критерии выполнения, зависимости, применимость к Lite/Standard и допустимость исключения.

## Как проходить

1. Создайте отдельный паспорт для каждого клиентского сайта.
2. Агент читает шаблон и текущий паспорт, получает доступные следующие шаги. Не проводите весь опрос за один раз: начните с 2–3 вопросов о бизнесе, аудитории и цели.
3. Записывайте фактические ответы владельца в том же порядке, что и вопросы шага. Неизвестное оставляйте пустым; не выдумывайте ответы ради прогресса.
4. После согласования выполняйте работу в рамках предоставленных прав. Ответ на вопрос не означает разрешение на покупку домена, списание денег, удаление данных или публикацию.
5. После проверки заполните `evidence`: что проверено, когда, кем, ссылка или путь к обезличенному доказательству. Затем установите `done`.
6. Получите список/граф и следующие шаги. До устранения обязательных пробелов рабочий запуск не считается принятым.

Внутренний паспорт не является контекстом публичного консультанта. Только отдельно одобренные публичные факты переносятся в контент сайта; разрешённые внутренние инструкции — в настройки консультанта. В Lite `site.config.json` публичен.

## Локальный инструмент

### Проверка исходников перед приёмкой

```bash
npm run launch -- audit --mode lite
npm run launch -- audit --mode lite --json
npm run launch -- audit --mode lite --output .northstar-launch/source-audit.md
```

Команда проверяет локальный `site.config.json`, название/описание/тему, уникальность ЧПУ и конфликты с системными маршрутами, структуру карточек/цен, наличие активного каталога, локального фона, стандартного favicon и исходников robots/sitemap/llms. Каждый результат содержит стабильный `id`, `taskId` из чеклиста, статус и конкретное следующее действие. JSON можно читать внешнему агенту; Markdown — владельцу. Отчёт не включает значения настроек, контент страниц, названия клиента, URL изображений или ответы паспорта.

Четыре статуса: `pass` — указанная локальная проверка пройдена, `warn` — требуется решение владельца, `fail` — обнаружена ошибка, `manual` — автоматическая проверка не выполнялась. Например, пустой каталог — предупреждение, а дублирующиеся адреса — ошибка. Проверки ЧПУ и карточек задают консервативные критерии подготовки, а не заменяют все runtime-валидаторы движка. Для Standard содержимое D1 не оценивается по локальному JSON: вместо ложного успеха выдаётся указание проверить админку.

Наличие SVG или файла маршрута **не означает**, что favicon подключён или HTTP-маршрут работает. Домен/DNS/HTTPS, реальный AI, разрешения, юридические требования и бизнес-приёмка остаются отдельными проверками. Аудит не обращается в сеть, не читает `.env`, D1 или паспорт, не запускает код конфигурации и не меняет статусы. Символические ссылки/junctions к проверяемым файлам запрещены; входные файлы ограничены по размеру. Не редактируйте дерево файлов одновременно с проверкой.

Обычная команда возвращает exit code 1 при `fail`; `--require-pass` также блокирует `warn`. Результаты `manual` остаются ручными даже при exit code 0: это **не разрешение на публикацию и не процент готовности**. Используйте вместе с `launch status --require-ready` и фактической приёмкой. Для Standard передайте `--mode standard` явно. Вывод создаётся только в новом файле вне public/dist; старый отчёт не перезаписывается. Родительский каталог должен существовать.

### Мастер без редактирования JSON

Во вкладке **«Аудит сайта»** нажмите **«Открыть отчёт JSON»** и выберите результат `launch audit --json --output …` (не JSON-паспорт и не Markdown). По умолчанию показаны ошибки, предупреждения и ручные проверки; фильтр позволяет посмотреть все результаты или отдельный статус. Кнопка «К шагу» открывает соответствующие вопросы, но не заполняет ответы и не отмечает шаг выполненным.

Импорт отчёта ограничен 256 КиБ: проверяются версия, структура, уникальные ID, известные шаги и совпадение счётчиков с результатами. Некорректный файл не заменяет ранее открытый отчёт и не стирает черновик. Текст файла не исполняется, URL не открываются автоматически. При несовпадении Lite/Standard появляется предупреждение. Даже совпадение режима не доказывает, что отчёт относится к этому сайту или актуален: после правок создайте новый отчёт.

Отчёт хранится только в текущей вкладке, не входит в сохранённый JSON-паспорт и убирается при открытии другого паспорта. «Убрать отчёт» очищает только просмотр, не удаляет файл. Автономный HTML поддерживает тот же импорт без сервера, сети и базы.

#### Сверка после изменений

Новые отчёты имеют версию 2: `generatedAt` (локальные часы, UTC) и `source` с SHA-256, областью `checked-inputs-v1`, числом прочитанных файлов и признаком полноты. Версия 1 остаётся доступной для просмотра, но без сверки. Это версия отчёта аудита, не версия JSON-паспорта владельца.

1. Откройте исходный отчёт во вкладке «Аудит сайта».
2. В каталоге нужного сайта заново выполните `npm run launch -- audit --mode lite --json --output .northstar-launch/source-audit-new.json` (для Standard измените режим; всегда выбирайте новое имя).
3. Нажмите **«Сверить с новым отчётом»** и выберите новый JSON. Основной отчёт, ответы и статусы останутся прежними.

Отпечаток учитывает режим, байты кода проверок и те же байты файлов, которые прочитал аудит: `site.config.json`, стандартный favicon, исходники robots/sitemap/llms и локальный фон, когда он задан. Пути, URL и содержимое в метку не включаются открытым текстом. Пробелы и переводы строк тоже влияют на результат. Совпадение не зависит от расположения каталога: две одинаковые копии дадут одинаковую метку, поэтому она **не является ID клиента**.

Мастер различает совпадение, изменение, неполное чтение, разные режимы, старый формат, более раннюю дату второго отчёта и противоречивые результаты при одинаковом отпечатке. Повреждённый файл сбрасывает прежнее подтверждение сверки, но сохраняет основной отчёт и черновик. Новый основной отчёт или другой паспорт сбрасывают сверку.

Сверяются заявления **двух выбранных файлов**, а не автоматически текущее состояние диска. Дата зависит от часов компьютера; можно выбрать старую копию дважды. Метка не подписана, её можно подделать; используйте отчёты, самостоятельно созданные доверенной копией движка. Не меняйте исходники во время аудита: чтение нескольких файлов не является атомарным снимком. Это не хеш всей сборки, не проверка опубликованного Worker, D1, секретов, DNS, внешних изображений или AI. Даже совпадение не закрывает ручную приёмку.

```bash
npm run launch:ui
```

Команда выводит локальный адрес `http://127.0.0.1:ПОРТ/`. Откройте его в браузере. В мастере нажмите **«Открыть файл»** и выберите `.northstar-launch/state.json` (для OraVera в нём уже есть сведения о размещении). Паспорт не читается сервером автоматически: файл выбирает владелец.

Заполните вопросы, доказательство и статус. **«Применить шаг»** обновляет черновик в текущей вкладке. **«Сохранить JSON»** сохраняет паспорт в выбранный файл через системный диалог; если браузер не поддерживает такой диалог, начинается скачивание — проверьте папку загрузок. В этом случае предупреждение при закрытии остаётся, поскольку браузер не подтвердил запись. **«Скачать чеклист»** выдаёт обезличенный Markdown-отчёт и не заменяет сохранение JSON с ответами.

Есть граф с переходом к узлам, список этапов и выбор следующего доступного шага. Изменение режима здесь меняет только паспорт, не переводит сайт из Lite в Standard. Некорректный импорт не заменяет черновик; отмена сохранения не считается успехом. Перед заменой изменённого паспорта запрашивается подтверждение. Не открывайте один файл на запись одновременно в нескольких мастерах: согласование изменений между файлами не реализовано.

Автосохранения, localStorage и облачной синхронизации нет. Файл — постоянное хранилище, вкладка — только черновик. При перезагрузке несохранённое теряется; мастер предупреждает перед закрытием, насколько это позволяет браузер. Храните JSON вне public/dist и публичного репозитория.

CLI по умолчанию продолжает читать `.northstar-launch/state.json`. Если мастер сохранил `launch-state.json` в Загрузки, укажите этот файл через `--state` или вручную перенесите проверенный результат в рабочий каталог. Скачивание копии не обновляет исходный файл автоматически.

Для работы совсем без сервера создайте автономный HTML:

```bash
npm run launch -- wizard --output .northstar-launch/wizard.html
```

Откройте этот HTML в браузере, затем импортируйте JSON. HTML содержит только шаблон и код, не ответы. Нет CDN, внешних скриптов и сетевых вызовов; CSP блокирует соединения. Локальный сервер привязан только к 127.0.0.1, отдаёт только интерфейс, не принимает изменения, не читает паспорт и не раздаёт каталог проекта. Закрытие сервера — Ctrl+C. Это **не удалённая админка и не MCP-сервер**.

### Проверка мастера при доработке движка

```bash
npx playwright install chromium
npm run test:launch-browser
```

Браузерный набор запускает отдельный Chromium и локальный сервер, использует только синтетические паспорта и не открывает `.northstar-launch/state.json`. Проверяет форму и зависимости, импорт и защиту черновика, скачивание JSON/Markdown, сохранение/отмену/ошибку записи, режимы Lite/Standard и ширины 320/390/1280 px с увеличением текста до 200%. Внешние запросы блокируются; ошибки JavaScript приводят к провалу проверки. JSON-отчёт и снимки сохраняются в новом `.test-state-launch-browser-*` и собираются в CI.

Системный файловый диалог заменён имитацией File System Access API: настоящий диалог ОС, Safari/Firefox и физические мобильные устройства требуют отдельной ручной проверки. Эмуляция ширины не заменяет такую приёмку.

Импорт и экспорт JSON ограничены 512 КиБ (байты UTF-8). Если суммарные ответы слишком велики, сохранение не начинается, а черновик остаётся в форме. При попытке завершить шаг без обязательных ответов или доказательства мастер выделяет первое незаполненное поле и переводит туда фокус.

### CLI для внешнего агента

```bash
# Один раз в отдельном checkout клиентского сайта
npm run launch -- init --mode lite

# После заполнения .northstar-launch/state.json
npm run launch -- status
npm run launch -- status --json
npm run launch -- report --output .northstar-launch/report.md

# Gate: ненулевой exit code, если паспорт ещё не закрыт
npm run launch -- status --require-ready
```

Для Standard передайте `--mode standard` при создании. По умолчанию состояние лежит в `.northstar-launch/state.json`, каталог исключён из Git и не находится в public/dist. Для другого файла используйте `--state PATH`; родительский каталог должен уже существовать. Пользовательский путь нужно самостоятельно исключить из публикации и системы контроля версий.

`init`, `report` и `guide` создают только новые файлы и **не перезаписывают существующие**. Для следующего отчёта выберите новое имя. Ответы владелец или уполномоченный внешний агент редактирует в JSON-файле обычным файловым редактором. Инструмент ничего не отправляет в сеть, не вызывает AI, не подключает домены и не меняет бизнес-настройки.

Чтобы получить чистый чеклист для другого режима:

```bash
npm run launch -- guide --mode standard --output .northstar-launch/standard-guide.md
```

Mermaid-граф встроен в Markdown; если просмотрщик не умеет его рисовать, ниже остаётся обычный полный список.

## Статусы и зависимости

- `todo` — не начато.
- `in_progress` — собираем ответы или выполняем работу.
- `done` — на все вопросы шага есть ответы и записано доказательство проверки.
- `not_applicable` — только необязательный шаг и только с непустым `reason`. Например, звонки или встроенная оплата не нужны в первом запуске.
- `blocked` — вычисляемый статус: предшествующие шаги не закрыты. Даже вручную поставленный `done` не закрывает зависимость.
- `out_of_scope` — вычисляется по режиму. Например, проверка кабинета исключена для Lite.

Пример одной записи (остальная структура сохраняется):

```json
{
  "status": "in_progress",
  "answers": ["Есть логотип, отдельного favicon пока нет", "Согласованный знак бренда"],
  "evidence": "",
  "reason": ""
}
```

Это пример шага `favicon`, не весь файл паспорта. Порядок и число ответов соответствуют `questions` в шаблоне. Не добавляйте произвольные поля: неизвестные ID, версии и неверные статусы отклоняются. При обновлении версии шаблона перенос ответов требует явного сопоставления, автоматического сброса нет.

Процент — **доля закрытых пунктов применимого плана**, включая явно исключённые необязательные шаги. Это не оценка качества движка и не доказательство работоспособности. Статусы и evidence вводит проверяющий; наличие favicon, привязка домена, работа AI и платежей сами по себе этим инструментом не проверяются. Gate подтверждает заполнение и зависимости, а не истинность ответов.

## Граница доступа для агента

Публичный MCP/llms не получает ответы, evidence или готовность конкретного клиента. Паспорт доступен через локальный мастер, файлы и CLI; встроенного веб-мастера в админке и нового MCP-инструмента записи нет.

`status --json` выдаёт статусы, зависимости, критерии и следующие вопросы **без ответов, названия клиента и evidence**. Markdown-отчёт также не включает эти поля. Нельзя хранить в паспорте пароли, cookies, ключи API, платёжные реквизиты, клиентские диалоги или дампы. Даже несекретные внутренние ответы могут быть конфиденциальными: ограничьте доступ к каталогу и резервным копиям. На Windows используйте права доступа ОС; POSIX-режим файла не заменяет Windows ACL.

## Что спросить первым у OraVera

1. Чем занимается OraVera и кто её клиент?
2. Какое главное действие должен совершить посетитель после диалога?
3. Какой язык сайта и общения?

Публичный технический адрес уже есть; это можно подтвердить [отчётом установки](ORAVERA.md), но собственный домен, содержание, favicon бренда и реальный консультант ещё требуют отдельных решений и проверок. Не отмечайте весь паспорт выполненным на основании этого отчёта.
