# Запись на услуги

Это собственный модуль движка на D1 с провайдер-независимым контрактом оплаты. Внешний календарь и платёжный адаптер подключаются отдельно. Один слот — один клиент. Администратор задаёт конкретные интервалы для ресурса (специалиста, кабинета, оборудования) и опубликованной услуги каталога.

## Как использовать

1. Создайте и опубликуйте услугу в каталоге.
2. Откройте `/admin#bookings`, добавьте ресурс и часовой пояс IANA, например `Europe/Moscow`.
3. Выберите ресурс и услугу, задайте начало/окончание слота в часовом поясе ресурса. Длительность — 5 минут–12 часов; начало в будущем, не позднее чем через 366 дней. Пересекающиеся интервалы одного ресурса запрещены, соседние разрешены.
4. На публичной карточке услуги и в `/account#bookings` клиент выбирает свободное время и подтверждает запись. Для записи нужен вход; свободные слоты видны без авторизации. Бесплатная запись подтверждается сразу, платная удерживает слот на 15 минут до оплаты.
5. В кабинете доступны собственные записи, комментарии, история, перенос и отмена будущей подтверждённой записи. Перенос — только на свободный слот той же услуги. Снимок первоначальной цены и названия сохраняется.
6. В админке видны записи всех клиентов. Завершить услугу можно только после её окончания. Администратор может отменить запись, в том числе прошедшую; денежные статусы при этом не меняются.

Поиск показывает неделю с указанной даты, границы окна поиска — UTC. Само время всегда подписано часовым поясом ресурса. В API можно запросить окно до 31 дня. Списки ограничены 200 записями; `truncated` сообщает о превышении лимита. В этой версии нет полноценной пагинации.

При изменениях из другой вкладки или агента устаревшая `revision` получает 409. Обновите данные перед повтором. Для создания записи при потере ответа повторяйте тот же Idempotency-Key и payload; после переноса/отмены с потерянным ответом сначала прочитайте запись и историю. Новый ключ при повторе не гарантирует дедупликацию.

## Закрытие и сохранение истории

Закрытие ресурса/слота запрещает новые записи, но не отменяет уже подтверждённые. Слоты неизменяемы по услуге, ресурсу и времени; их можно закрыть/открыть. Закрытый слот продолжает резервировать интервал расписания — это не удаление. Услугу с расписанием можно скрыть, но нельзя удалить через каталог. Старые свободно заданные записи без `slot_id` остаются видимыми только своему клиенту/администратору и доступны только для чтения: фиктивные слоты при миграции не создаются.

Дата хранится в UTC (Unix seconds), ресурс хранит IANA time zone. UI отклоняет отсутствующее и неоднозначное локальное время при переводе часов, а не переносит встречу молча. Для неоднозначного времени администратор может использовать API с точным ISO 8601 и явным UTC-смещением. Браузерный выбор времени сам по себе не устанавливает бронь.

## REST / MCP

- `GET /api/booking-slots`: публичная доступность; `productId`, `from`, `to`. `managed=1` требует owner/admin и возвращает также ресурсы/закрытые/занятые слоты, без данных клиентов.
- `POST /api/booking-slots`: owner/admin; `create_resource`, `set_resource`, `create_slot`, `set_slot`.
- `GET /api/bookings`: собственные записи клиента; администратору — все, с `mine=1` только собственные.
- `POST /api/bookings`: `slotId`, необязательный `customerNote`; заголовок `Idempotency-Key` обязателен. Только администратор может передать `customerId` другого пользователя.
- `POST /api/bookings/{id}/checkout`: запрашивает HTTPS-ссылку у внешнего адаптера или встроенного Stripe Checkout (`PAYMENT_PROVIDER=stripe`) для платной записи в период удержания. Оплату подтверждает только проверенный webhook.
- `POST /api/bookings/{id}/refund`: owner/admin-only полный возврат через встроенный Stripe-адаптер для записи со статусом `paid`; операция идемпотентна.
- `POST /api/webhooks/booking-payment`: webhook адаптера с `x-payment-secret`; проверяет intent, booking, сумму, валюту, срок удержания и идемпотентность события.
- `POST /api/webhooks/stripe`: Stripe webhook с обязательной проверкой сырого тела и `Stripe-Signature`; поддерживает Checkout completed/async success/failure/expired.
- `GET /api/bookings/{id}`: приватная запись и история.
- `PATCH /api/bookings/{id}`: `action: cancel|reschedule|complete`, `revision`; для переноса ещё `slotId`.

Контракты, типы, единицы и ошибки опубликованы в `/api/openapi`. Запись API из браузера защищена проверкой origin, ограниченным JSON и rate limit: создание/изменение записи — по 20/минуту на аккаунт, изменение расписания — 40/минуту. REST и MCP используют общие бизнес-функции и лимиты.

Клиентскому агенту выдайте `bookings:read` и при необходимости `bookings:write`. Ему доступны `list_booking_slots`, `list_bookings`, `get_booking`, `create_booking`, `checkout_booking`, `update_booking`. `refund_booking` доступен только owner/admin MCP и не показывается клиенту. Чужая запись не открывается даже по известному ID. Агент не может завершить услугу, изменить цену/статус оплаты или управлять ресурсами. До вызова создания/переноса/оплаты агент должен согласовать услугу и время с клиентом; движок не может проверить содержание внешнего диалога агента.

Владельцу доступны также `list_booking_schedule` (ресурсы/управляемые слоты) и `manage_booking_schedule` (создать ресурс/слот, открыть/закрыть). Требуются соответствующий scope и роль владельца/администратора. Созданные прежде токены не получают новые scopes автоматически.

Изменение старого MCP-контракта: `list_bookings` теперь возвращает `{ bookings, truncated }`; `update_booking` вместо свободного `service/startsAt/status` принимает ограниченные `action/revision/slotId`. Это намеренно закрывает обход защиты слотов. Инструменты и параметры сверяйте через `tools/list`.

## Надёжность и миграция

Миграция `0007_bright_peter_quill.sql` добавляет ресурсы, слоты, историю и nullable-поля к старым бронированиям. Ничего не удаляется, прежние миграции не переписываются. Новую миграцию нужно применить до запуска обновлённого Worker; сначала проверьте на копии базы.

Создание слота проверяет пересечение и записывает интервал одним SQL-запросом. Частичный уникальный индекс разрешает только одну активную `confirmed` или `pending_payment` запись на слот. Бронирование и событие записываются в D1 batch; перенос одним UPDATE меняет слот только при совпадении revision и доступности нового места. История добавляется только для действительно выполненной мутации. При ошибке события batch откатывается. Просроченное удержание платной записи автоматически переводит её в `cancelled/expired` при следующем чтении расписания.

Первичные источники: [транзакции D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/), [уникальные частичные индексы SQLite](https://www.sqlite.org/partialindex.html). Поведение дополнительно проверяется конкурентными запросами и искусственным отказом записи события в отдельной тестовой D1.

## Что ещё не реализовано

- Повторяющийся график, праздники/отпуска, буферы между встречами, групповые места и несколько ресурсов на запись.
- Редактирование/пакетный перенос самих интервалов, переименование ресурсов, поиск и полноценная пагинация.
- Подключение конкретного платёжного провайдера, чек/возврат на его стороне, связь платежа с заказом и сверка выплат.
- SMS/email, календарные интеграции и напоминания.
- Вызов записи непосредственно текстовым консультантом: клиентский MCP уже работает, tool-calling консультанта — отдельная задача.
- Сквозная проверка UI на реальных мобильных устройствах и production-приёмка.

Это рабочая запись на конкретное время, а не готовая замена полнофункциональной системе расписаний.
