# OraVera — подготовка стоматологического сайта

Подтверждено владельцем: стоматологическая клиника в Майами; посетитель может задать вопрос, приложить фото полости рта и запросить очный осмотр. Начальный язык — английский. Адрес, телефон, врачи, часы, страховки, стоимость и свободные слоты пока неизвестны. Они не выдуманы и не заменены бесплатными товарами.

## Текущий вариант: Standard с кабинетом пациента

По решению владельца OraVera переведена **локально** на Standard с D1. Общий Lite остаётся доступным без базы. `SITE_PRESET=oravera` выбирает оформление независимо от режима; старое `LITE_SITE_PRESET` поддерживается как резервное имя. `deployment/oravera.lite.json` и удалённый сайт не изменены, облачная D1 не создана.

После сборки запуск: `npm run start:oravera`. Скрипт применяет существующие миграции к отдельной локальной D1 в `.oravera-standard-local/` и запускает сайт на порту 8787. Данные сохраняются между перезапусками. Старые `.wrangler-state/` и `.northstar-launch/` не переносит и не заменяет. Нет новых схем, зависимостей или R2. `deployment/oravera.standard.local.json` содержит фиктивный идентификатор локальной базы и **не предназначен для deployment**.

Первый владелец регистрируется на `/login`: Create a patient account → Clinic owner setup. Случайный `INITIAL_ADMIN_TOKEN` автоматически создан в игнорируемом локальном `.oravera-standard-local/.env`; скрипт не печатает его и не заменяет при повторном запуске. Это не пароль. Email и пароль владелец задаёт самостоятельно; последующие регистрации создают клиентов без административных прав. Не переносить локальный код в production.

- [x] Ссылка Patient account на главной; английские регистрация и вход используют существующие API авторизации Standard.
- [x] `/account` и `/admin` проверяют браузерную сессию до рендера; клиент не получает админку. Кабинет отдаётся с private/no-store и noindex.
- [x] Кабинет читает `/api/bookings?mine=1`: предстоящие и прошлые/отменённые записи, услуга, ресурс/врач, дата, время, статус и номер записи. Время показано в часовом поясе записи, резервный пояс — America/New_York. Неизвестный адрес не выдумывается.
- [x] Подтверждённая запись отличается от ожидания оплаты и существующих неподтверждённых записей. Прошедшая дата сама по себе не помечает визит «завершён».
- [x] Контактные данные пациента, ручное обновление, обновление после возвращения во вкладку, понятная ошибка загрузки вместо ложного пустого списка, отзыв сессии при выходе.
- [x] Данные хранятся в D1, не в браузере. Клиент не видит чужие записи даже при подмене ID. Администратор в своём кабинете тоже видит только свои записи; общий список остаётся в админке.
- [x] Новая локальная база не заполнена демонстрационными врачами, ценами и пациентами. Тестовые записи создаются исключительно в изолированных `.test-state-*`.
- [ ] Настроить реальные услуги, врачей/ресурсы, расписание и связи с аккаунтами пациентов. Готовые Standard API/MCP поддерживают создание администратором записи для конкретного `customerId`; на новом экране пока **просмотр**, не самостоятельная запись/перенос/отмена.
- [ ] Подключить клинический рабочий процесс и условия обработки данных. В OraVera Standard сейчас жёстко закрыты маршруты чата, файлов, звонков и прежней внешней формы — даже включение общих AI-флагов их не открывает. Медицинские фото не сохраняются; включение потребует отдельной проверенной реализации. Lite-вариант ниже остаётся отдельным прототипом.
- [ ] Перенос внешней заявки в запись пока не автоматизирован. Кабинет не превращает письмо/диалог в подтверждённый визит. Отдельного интерфейса создания новой заявки со статусом pending пока нет.
- [ ] Кабинет читает последние 200 записей и предупреждает об ограничении; полноценная пагинация более длинной истории остаётся доработкой.
- [ ] Перед production: утвердить privacy-текст, контакты, домен, поставщиков, доступ/сроки хранения/резервные копии; отдельно создать D1 и принять облачный deployment. Локальная работоспособность не подтверждает готовность к данным пациентов.

Проверка: `npm run test:oravera-account` поднимает изолированную D1 без R2, регистрирует синтетические аккаунты, создаёт реальные записи через API и проверяет их разделение, мобильный UI, ошибки, выход и сохранность после перезапуска Worker. Отдельная синтетическая legacy-pending запись нужна только для проверки отображения статуса.

## Предыдущий вариант: Lite-профиль без кабинета

`presets/oravera.json` — публичные сведения и страницы. `LITE_SITE_PRESET=oravera` выбирает профиль на сервере. Без него остаётся обычный `site.config.json`. Движок остаётся универсальным, Lite работает без D1/R2. Изменения этого этапа не развёрнуты в Cloudflare и не переписывают паспорт владельца.

Локальный просмотр после `npm run build`:

```powershell
node node_modules/wrangler/bin/wrangler.js dev --local --config deployment/oravera.preview.json --port 8787 --inspector-port 0
```

Это конфигурация предпросмотра, не конфигурация запуска для пациентов. Все каналы передачи данных выключены. Favicon — временная буквенная иконка, не утверждённый фирменный знак.

## Перед приёмом пациентов

- [x] Чат — главный экран, английские страницы, мобильная компоновка.
- [x] Отдельные сведения об осмотре, фото и подготовке обработки данных.
- [x] Загрузка JPG/PNG/WebP до 2 МиБ; явное согласие взрослого посетителя перед каждой передачей сообщения, контекста и выбранного фото.
- [x] Фиксированные инструкции: AI не стоматолог, не ставит диагноз по фото, не назначает лечение, не подтверждает запись. Экстренная подсказка видна вне AI-чата.
- [x] Отдельная форма запроса на осмотр: имя, контакт и предпочтительное время; переписка и фото не включаются. Получение заявки не равно подтверждению визита.
- [x] До активации медицинской обработки сервер отвергает чат/фото и выключает заявки. Голос в стоматологическом профиле отключён независимо от общего переключателя.
- [ ] Подтвердить название, адрес, телефон, часы, врачей и канал получения заявок.
- [ ] Утвердить английский текст и необходимость испанской локализации; не считать автоматический ответ AI полной локализацией сайта.
- [ ] Определить расписание и процедуру подтверждения, отмены и переноса записи. Сейчас это **запрос на осмотр, не интеграция с календарём**.
- [ ] Определить юридические обязанности клиники и подходящие продукты поставщиков, договоры/BAA при необходимости, сроки хранения/удаления и доступ к данным. Проверить AI, Cloudflare, получателя заявок и их журналирование, не только движок.
- [ ] Опубликовать утверждённые условия и контакты для запросов о данных. Текущая `/privacy` — предупреждение о подготовке, не готовая политика конфиденциальности.
- [ ] Утвердить медицинские ограничения у стоматолога и проверить реальные ответы модели на синтетических сценариях: симптомы, фото, экстренные сообщения, prompt injection, другие языки. Тест наличия инструкции не доказывает безопасность ответов.
- [ ] Настроить секрет выбранного AI, лимиты и получателя заявок с дедупликацией ID. Не помещать секреты в публичный JSON.
- [ ] Только после проверки установить `LITE_HEALTH_DATA_ENABLED=true` вместе с необходимыми AI/lead-настройками. Это подтверждение владельца, **не автоматическая проверка соответствия требованиям**.
- [ ] Подтвердить домен и пройти отдельную production-приёмку. Не использовать данные реальных пациентов для тестового запуска.

Фото отправляется выбранному AI-провайдеру, **не врачу**; отдельного кабинета клинического просмотра и медицинской карты в Lite нет. Движок не сохраняет историю/файлы в БД или R2, но это не обещание отсутствия обработки/хранения у поставщиков. При неполученном ответе UI не делает автоматических повторов: новая попытка может повторно передать данные и стоить денег. Запросы на запись используют отдельный согласованный ID для явного повтора.

## Проверки

`npm test`, `npx tsc --noEmit`, `npm run build`, `npm run test:lite`, `npm run test:oravera`.

OraVera-набор поднимает два изолированных локальных Worker. Проверяет закрытые серверные маршруты, обязательное согласие, публичные страницы/Markdown, 320/390/1280 px и 200% текста, загрузку синтетического изображения и отдельную форму. Разрешённый AI-ответ и получатель формы подставные; браузерные внешние запросы блокируются. Для UI включённой конфигурации используется заведомо фиктивный ключ. Ни платный провайдер, ни фактическая доставка, ни клиническое качество здесь не проверены.

Основания ограничений: [ADA — teledentistry](https://www.ada.org/about/governance/current-policies/ada-policy-on-teledentistry), [HHS — cloud computing](https://www.hhs.gov/hipaa/for-professionals/special-topics/health-information-technology/cloud-computing/index.html), [HHS — business associates](https://www.hhs.gov/hipaa/for-professionals/privacy/guidance/business-associates/index.html). Пример признаков, требующих экстренной помощи: [NHS — dental abscess](https://www.nhs.uk/conditions/dental-abscess/); на сайте Майами указан местный номер 911.
