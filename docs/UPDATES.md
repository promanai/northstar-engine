# Обновления из GitHub

В админке появился раздел **Обновления**. Владелец выбирает `owner/repository` или ссылку GitHub, проверяет последний стабильный релиз, включает автоматический режим или ставит установку в очередь. История хранится в D1. По умолчанию источник пустой, автоматика выключена.

Это обновление кода установленного движка, не синхронизация произвольного сайта и не SaaS. Репозиторий должен содержать совместимый движок, `engine-release.json`, неизменённые старые миграции и рабочие команды сборки/тестов. Для своих доработок используйте собственный fork и выпускайте релизы в нём: обновление заменяет код, не выполняет merge.

## Однократное подключение

1. Создайте собственный управляющий репозиторий с этим исходным кодом, включая `.github/workflows/engine-update.yml`, `scripts/update-runner.mjs` и lockfile. Workflow должен находиться в основной ветке; включите Actions и расписание для fork. Репозиторий исполнителя может совпадать с источником релизов, но не обязан.
2. В управляющем репозитории скопируйте `deployment/worker.example.json` в `deployment/worker.json`. Укажите **существующие** имя Worker, ID/имя D1, имя R2, собственные routes/custom domains и остальные bindings, необходимые вашей установке. Не копируйте локальные placeholder ID. В файле не должно быть секретов. Этот конфиг является источником параметров деплоя; настройки чужого релизного репозитория не используются.
3. Соберите текущую версию (`npm ci`, `npm run build`). Для новой пустой БД примените миграции: `npx wrangler d1 migrations apply DB --remote --config deployment/worker.json`. Затем разверните Worker: `npx wrangler deploy --config deployment/worker.json --keep-vars`. Для старой установки сначала сверяйте фактическую схему и учёт миграций, как описано ниже. Сайт должен быть доступен исполнителю по HTTPS, например через workers.dev или свой домен. GitHub Actions не может обратиться к вашему `127.0.0.1`.
4. Создайте случайный секрет исполнителя длиной минимум 32 символа. Сохраните одинаковое значение в Cloudflare Worker secret `UPDATE_RUNNER_SECRET` и в GitHub Actions secret `UPDATE_RUNNER_SECRET`. На Worker задайте `UPDATE_RUNNER_REPOSITORY=ваш-владелец/управляющий-репозиторий`. Не используйте для этого пароль администратора, MCP-токен или ключ AI.
5. В GitHub Actions задайте variable `ENGINE_SITE_URL` — только HTTPS-origin сайта, без пути/query. Добавьте secrets `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID`. Ограничьте Cloudflare token аккаунтом и нужными правами для Worker/D1; при routes нужны соответствующие права зоны. Не храните его в админке или исходниках.
6. Для приватного источника дополнительно задайте Worker secret `GITHUB_RELEASE_TOKEN` (чтение Releases/Contents выбранного источника) и Actions secret `SOURCE_READ_TOKEN` (чтение исходного репозитория). При смене приватного репозитория проверьте доступ обоих токенов. Для публичного источника эти секреты не обязательны.
7. В админке выберите источник, подтвердите доверие к его коду и сохраните. Нажмите **Проверить GitHub**. Для первого пробного обновления подтвердите доверие и поставьте установку в очередь. В Actions запустите **Engine update → Run workflow** из основной ветки. Проверяйте журнал и установленный SHA, затем при желании включите автоматический режим отдельным сохранением.

Workflow планирует проверку каждый час, на 17-й минуте. GitHub может задержать или отключить расписание; это не гарантия проверки в точную минуту. Очередь из админки забирается следующим запуском. Кнопка постановки в очередь не вызывает GitHub workflow немедленно. **Обновить статус** получает актуальный результат без изменения настроек. Наличие секрета в UI ещё не означает успешное подключение — смотрите «Последний контакт» и журнал Actions.

## Правила установки

- Только стабильные Releases с тегом `vMAJOR.MINOR.PATCH` или `MAJOR.MINOR.PATCH`, не draft/prerelease. Источник — GitHub `releases/latest`, затем тег фиксируется в полный commit SHA.
- Автоматически ставится только более новая версия того же major. Переход major требует ручного выбора. Понижение версии через этот механизм запрещено. Другой fork/commit той же версии можно установить вручную.
- Смена репозитория очищает найденный релиз и всегда выключает автоматический режим. Требуется новое подтверждение доверия. Код выбранного источника после деплоя получает доступ к данным и runtime-секретам Worker.
- Редактировать эти настройки может только cookie-сессия владельца. Обычный клиент и существующий MCP-токен не получают право менять цепочку обновления. Исполнитель использует отдельный секрет; он может забрать и завершить только серверное задание, но не изменить источник.
- Очередь и запуск защищены версией записи D1. Второй исполнитель не получает то же задание. Отменить можно только ещё не забранное задание. Настройки блокируются на время задания.
- Сначала сборка и тесты в отдельном job без Cloudflare/runner-секретов, затем упаковка и отдельный job деплоя. Управляющий репозиторий остаётся доверенным: его scripts и workflow необходимо защищать от чужих изменений.
- Статус «Установлено» подтверждается только когда работающий Worker возвращает встроенные при сборке ожидаемые repository/version/SHA. Сам факт успешного запуска workflow недостаточен. Повтор завершения идемпотентен.
- Неудачный SHA автоматически повторно не ставится. Для осознанной повторной попытки используйте ручную очередь. Зависший запуск старше двух часов следующий запрос исполнителя помечает ошибкой; сначала проверьте фактическое состояние Worker и БД.

## Данные и миграции

Миграция `drizzle/0005_curved_doctor_strange.sql` добавляет только таблицу состояния обновлений. Существующие пользователи, сессии, заказы, настройки и R2-файлы не изменяются этой миграцией.

В текущем рабочем проекте 0005 уже применена локально и не требует повторного запуска.

Автоустановка проверяет SHA256 существующих SQL-файлов, нормализуя CRLF/LF, и запрещает их изменение/удаление. Новые миграции допускаются консервативным фильтром: `CREATE TABLE`, `CREATE INDEX`, `ALTER TABLE … ADD`. Удаление/переименование/перенос данных требуют отдельно проверенного ручного обновления. Фильтр не заменяет ревью SQL, проверку совместимости и резервные копии. Старый Worker должен продолжать работать с новой схемой, пока выполняется деплой.

**У старых установок, где SQL применялся через `d1 execute`, может отсутствовать `d1_migrations`. Нельзя сразу запускать весь набор `migrations apply`: он попробует повторно создать существующие таблицы.** До подключения автоматики оператор должен проверить схему/выполненные SQL, сделать резервную копию и восстановить корректный учёт уже применённых миграций по инструкции D1. Не отмечайте миграцию выполненной только по совпадению имени. В текущей локальной установке 0000–0004 уже применены напрямую; новую 0005 нужно применять отдельно один раз, не повторяя старые.

Исполнитель применяет новые миграции до замены Worker. Автоматического отката БД нет. Частичный отказ требует проверки журнала миграций и состояния Worker, а не безусловного повторного запуска. Настройте резервное копирование/Time Travel и проверьте восстановление до включения автоматики. В репозитории есть локальные `db:preflight`, `db:backup` и `db:restore` с manifest/SHA-256 и явным подтверждением remote restore; инструкция — [docs/OPERATIONS.md](OPERATIONS.md). Remote backup/restore в аккаунте владельца остаётся обязательным приёмочным шагом. Деплой сохраняет runtime vars (`--keep-vars`); имена D1/R2 и остальные bindings берутся из доверенного deployment-конфига. Секреты не переносятся из исходного релиза.

## Проверки и ограничения

Локально проверяются политики GitHub с поддельными ответами, SemVer, фиксация SHA, ограничения миграций и изолированные HTTP/D1-сценарии прав, очереди, конкуренции и отчётов. Реальный GitHub Actions → Cloudflare deploy нужно пройти на отдельной тестовой установке после настройки репозиториев и секретов. Локальные тесты не доказывают доступность облачных credentials, успешность remote migrations или восстановление после аварии.

Команды: `npm test`, `npm run build`, `npm run test:integration`. Дополнительная проверка упаковки готовой сборки: `node tests/update-package.mjs`; результат остаётся в отдельном игнорируемом `.test-state-update-package-*`.

Официальные источники: [GitHub Releases API](https://docs.github.com/en/rest/releases/releases), [расписание GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), [миграции D1](https://developers.cloudflare.com/d1/reference/migrations/).
