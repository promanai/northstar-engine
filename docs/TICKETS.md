# Обращения клиентов — Standard

В кабинете `/account#tickets` клиент создаёт обращение и переписывается с владельцем сайта. В `/admin#tickets` администратор видит все обращения, отвечает, закрывает и повторно открывает их. Клиент может закрывать и повторно открывать только свои обращения. Это переписка с человеком, не автоматический AI-чат.

## Хранение и доступ

- Миграция `0017_lumpy_mojo.sql` добавляет `support_tickets` и `ticket_events`. Применяется штатным процессом миграций Standard; старые миграции не менялись. Не применяется к Lite.
- Существующие сессии и отзываемые API-токены. Только роли customer/admin/owner; неизвестные роли отклоняются.
- `tickets:read` разрешает чтение, `tickets:write` — отправку и изменение статуса. Права независимы; записывающий токен не получает содержание истории в ответе на изменение. Администратору с токеном также нужны соответствующие scopes.
- Все операции проверяют владельца на сервере. Чужое и отсутствующее обращение дают 404. Токен никогда не подменяется браузерной сессией при ошибке авторизации.
- Автор, его роль и идентификатор клиента определяются сервером; создать обращение от имени другого клиента нельзя даже администратору.
- История включает сообщения и закрытие/повторное открытие, но не секреты и не пароли. Ответы `private, no-store`. Текст выводится как текст, без HTML/Markdown-исполнения. Для агентов это недоверенное содержимое, а не инструкции к действию.
- Внешние ключи не позволяют удалить пользователя с обращениями/авторством и не удаляют переписку каскадно.

## REST и MCP

| REST                      | MCP             | Назначение                                        |
| ------------------------- | --------------- | ------------------------------------------------- |
| GET `/api/tickets`        | `list_tickets`  | Свои обращения; `all=true` — только администратор |
| GET `/api/tickets/{id}`   | `get_ticket`    | Карточка и последние сообщения                    |
| POST `/api/tickets`       | `create_ticket` | Создать обращение с первым сообщением             |
| PATCH `/api/tickets/{id}` | `update_ticket` | Ответить, закрыть, открыть снова                  |

Контракт опубликован в `/api/openapi`. Токены создаются в существующем разделе «AI-агенты». Новые полномочия не добавляются к уже выданным ограниченным токенам автоматически.

Создание требует `subject`, `body`, `confirm:true`, `idempotencyKey`. Изменение требует `action` (`message`, `close`, `reopen`), актуальную `revision`, `confirm:true` и `idempotencyKey`. Для `message` нужен `body`; для смены статуса поле `body` запрещено. Клиентский интерфейс отправляет подтверждение после явного нажатия соответствующей кнопки. Агент должен получить согласие пользователя перед изменением.

Ключ: 16–128 символов `A-Z a-z 0-9 _ -`, например UUID. Область ключа — автор, общая для REST/MCP и всех его обращений. При неизвестном результате повторять **тот же payload и ключ**. Точный повтор возвращает исходные метаданные `{id,eventId,revision,status,replayed}`, не создавая записи. Изменение параметров при прежнем ключе даёт 409. Метаданные повтора отражают первоначальную операцию, а не текущую версию карточки — для неё нужен отдельный GET.

Создание обращения/первого сообщения и изменение revision/добавление события выполняются атомарным D1 batch. Конкурентное изменение при прежней revision даёт 409. После конфликта нужно загрузить текущую переписку, сравнить её с черновиком и подтвердить новую отправку с новой revision/ключом. Нельзя автоматически обновлять revision и повторять запись вслепую.

## Ограничения

- Тема до 160 символов, сообщение до 8000; JSON REST до 40 000 байт.
- 30 попыток записи в минуту на пользователя, общие для REST и MCP; повторы и отклонённые запросы тоже учитываются. REST возвращает 429/Retry-After, MCP — ошибку инструмента. Это не общий денежный/дисковый бюджет сайта.
- До 2000 событий на обращение. После лимита нужна новая переписка. История не редактируется и не удаляется через API.
- Список: 50 записей, порядок по времени создания и ID по убыванию, `nextBefore` для следующей страницы. Это не сортировка по последнему ответу.
- История: последние 50 событий по revision, в хронологическом порядке. `nextBefore` запрашивает более ранние. Временные метки — Unix миллисекунды.
- Нет вложений, email/SMS/push-уведомлений, назначения оператора, поиска, realtime-обновления или автоматических ответов AI. Пользователь обновляет переписку кнопкой.
- Черновик и ключ незавершённой отправки хранятся только в памяти открытого раздела. После закрытия/перезагрузки нужно проверить список и историю перед новой отправкой: автоматическое восстановление незавершённой операции пока не реализовано. Интерфейс предупреждает об этой границе.
- Retention, выгрузка/анонимизация приватной истории и отдельный бюджет хранения пока не реализованы. D1-бэкап сохраняет эти таблицы вместе с остальными данными Standard.

Lite по-прежнему не имеет базы, кабинета и обращений: `/api/tickets` и вложенные пути недоступны, инструменты не публикуются в его MCP/OpenAPI.

## Проверка

`tests/ticket-policy.test.mjs`: роли/scopes, строгие поля, размеры, подтверждение, revision, курсоры.

`tests/tickets-integration.mjs` входит в изолированный Standard-прогон: реальные Worker/D1, владение, конкуренция/повторы, статусы, REST/MCP, откат при искусственной ошибке события, постраничная история/список, индексы через EXPLAIN QUERY PLAN и PRAGMA optimize, ограничения и OpenAPI. Рабочая база владельца не используется.

Результат итерации: 87 тестов политик/адаптеров/D1, 175 Standard и 10 Lite; сборка, TypeScript и lint прошли. Финальный Standard-прогон — `.test-state-C4cXsw`; подтверждён и откат удаления клиента, связанного только с обращением. Индекс административного списка дополнительно проверен на этой же изолированной базе.

Визуальная/мобильная и облачная приёмка нового раздела — отдельный незавершённый этап.
