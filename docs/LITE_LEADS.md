# Заявки в Lite без базы

Необязательный модуль «Оставить заявку» рядом с инструментами чата. Клиент сам заполняет имя, email/телефон и текст, видит получателя и условия обработки данных, затем явно подтверждает передачу. Переписка, вложения, cookies и IP не отправляются получателю. D1, R2, очередь и аккаунт не нужны.

По умолчанию модуль выключен. Это передача обращения внешнему сервису владельца, **не заказ, запись или оплата**. MCP остаётся read-only; универсального агентского оформления заказа этот модуль не добавляет.

## Чеклист подключения

- [ ] Выбрать контролируемый владельцем HTTPS-получатель. Проверить его условия, стоимость и правила хранения данных.
- [ ] Реализовать контракт ниже, аутентификацию и устойчивую дедупликацию по ID. Обычный webhook без этого контракта не подходит.
- [ ] Опубликовать страницу условий обработки данных, указать действующего получателя и контакт для проверки номера заявки. Наличие пути в настройке не проверяет содержание или юридическую достаточность страницы.
- [ ] В клиентском Wrangler-конфиге добавить `LITE_LEAD_LIMITER` (пример есть в `deployment/lite.example.json`): `namespace_id: "1003"`, `simple: { limit: 3, period: 60 }`. При совмещении нескольких сайтов подобрать отдельный namespace.
- [ ] Установить серверные secrets `LITE_LEAD_WEBHOOK_URL` и `LITE_LEAD_WEBHOOK_TOKEN` в выбранном Worker. Токен — 32–256 символов A–Z/a–z/0–9/дефис/подчёркивание, случайный, не пароль пользователя. Не коммитить secrets и не помещать их в публичную конфигурацию.
- [ ] В vars указать `LITE_LEADS_ENABLED: "true"`, `LITE_LEAD_RECIPIENT` (публичное название, до 120 символов), `LITE_LEAD_PRIVACY_PATH` (локальный ЧПУ-путь, например `/privacy`).
- [ ] Проверить тестовую заявку на специально выделенном получателе, повтор того же ID, отказ и потерю ответа. Не отправлять тесты реальным клиентам.
- [ ] Проверить опубликованный сайт: форма, согласие, ссылка на условия, фактическое получение и отсутствие дублей.

Уже развёрнутые клиентские конфиги не изменяются автоматически. Для выключения установить `LITE_LEADS_ENABLED: "false"`. При неполной конфигурации `GET /api/leads` вернёт `{ "enabled": false }`, кнопка не появится.

## Контракт получателя

Worker отправляет один `POST` с `Content-Type: application/json`, `Authorization: Bearer <secret>` и `Idempotency-Key: <UUID v4>`:

```json
{
  "version": 1,
  "id": "b47e7b7d-72d4-4af4-a04e-b5cdde45d168",
  "name": "Тест",
  "contact": "test@example.com",
  "message": "Тестовая заявка",
  "consent": true,
  "recipient": "Название получателя",
  "privacyPath": "/privacy"
}
```

Получатель проверяет секрет, схему и совпадение ID в заголовке и теле. Атомарно сохраняет заявку и ключ дедупликации. Повтор того же ID и тела возвращает прежнее подтверждение, не создаёт новую заявку/уведомление; повтор ID с другим телом отклоняет. Повторные действия ниже по цепочке также должны быть идемпотентными. Входной текст — недоверенные данные, не HTML и не инструкции для агента.

Только после устойчивого приёма возвращать HTTP 200 или 202 и JSON:

```json
{"accepted": true, "id": "b47e7b7d-72d4-4af4-a04e-b5cdde45d168"}
```

Без устойчивой дедупликации на стороне получателя подключать модуль нельзя. Движок не может проверить эту гарантию по одному HTTP-ответу.

## API и ограничения

`GET /api/leads` возвращает доступность, публичного получателя, путь условий и непрозрачный `configurationId`. URL и токен не раскрываются. `POST /api/leads` принимает ровно `id`, `name`, `contact`, `message`, `consent: true`, `configurationId`. Последний привязывает согласие к текущему получателю/URL/токену/пути условий; их смена отклоняет старую форму с 409 до отправки. Текст самой страницы условий в отпечаток не входит.

POST требует same-origin `Origin`, JSON, не принимает Bearer-авторизацию агента; это публичная форма, а не привилегированный API. Проверка Origin не является защитой от ботов: небраузерный клиент может подставить заголовок. Rate limiter ограничивает запросы по IP, не заменяет CAPTCHA, общую квоту или защиту получателя. Secrets доступны только доверенному владельцу развёртывания.

Имя ≤120, контакт ≤200, текст ≤4000 символов; тело ≤16 КиБ, ответ получателя ≤4 КиБ. URL — HTTPS-домен без credentials/query/fragment/нестандартного порта; IP, локальные суффиксы и редиректы запрещены. Проверка строки URL не удостоверяет публичность DNS-адреса: подключать только доверенный endpoint, контролировать DNS.

Успех клиенту возвращается лишь после подтверждения того же ID. При таймауте, редиректе, некорректном ответе или сбое после начала отправки результат **неизвестен**. Форма показывает номер, блокирует изменение полей и позволяет явно повторить только исходное тело с тем же ID. Автоматических повторов нет. Поздний отказ не отменяет неопределённость предыдущей попытки.

В Lite нет журнала заявок, фоновой доставки, проверки статуса или гарантии exactly-once. Черновик/номер живут в памяти вкладки, не сохраняются после перезагрузки. При неопределённом результате сначала сохранить номер и уточнить у получателя; новая вкладка/новая заявка может создать дубль. Ответ 202 подтверждает приём сервисом, а не прочтение человеком.

## Проверки движка

`npm test` проверяет серверную логику с подставным transport, без сетевой доставки. После `npm run build` команда `npm run test:lite` проверяет реальные Lite API с выключенной доставкой. Отдельная `npm run test:leads-browser` запускает свой локальный Worker без D1/R2: Chromium проверяет форму с подставленным `/api/leads`, мобильные размеры и текст 200%. Оба набора обязательны в CI. Эти проверки **не подтверждают** работоспособность внешнего получателя, Cloudflare deployment или физического телефона.
